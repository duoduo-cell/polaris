# 跟进卡、变化检测与态势报告（设计）

2026-10-24 夜，按 [场景调研](../research/2026-10-24-career-agent-scenario-update.md) 第 9 节第 1、2、3、6 项实现。云端部署、邮箱/日历连接器不在本轮（需要用户先定云、预算和授权）。

**10-25 已实现**：`polaris/watch.py`（建卡、检查、提醒、到期）、`polaris/watch_report.py`（态势报告）、`polaris/career_review.py`（HR 视角、同类对照）、工具 `watch_status`/`watch_create`/`profile_review`/`peers_compare`、网页“跟进”“竞争力”两页。和下文的差别：`watches` 多了 `state` 列（存上次检查时范围内在招岗位的编号，用集合比较代替时间戳，避免抽取晚到导致漏报）；重点岗位的下架和重新出现不在范围视角重复报；按入库时间找新内容时下界不早于开卡时刻。

## 1. 要解决什么

现在北极星的“主动”是全局的：按记忆卡片里的长期偏好，每天挑几条新内容推送。用户说“接下来两周帮我盯着北京的 Agent 日常实习，重点是这三个岗位”时，没有一个对象记住这个委托，也没有人负责回答“这几天发生了什么、对我有什么影响、我还差什么”。

跟进卡就是这个委托：**一个有范围、有期限、可暂停的长期目标**。采集照旧由常驻采集负责；跟进卡负责按自己的范围看变化、分级提醒、定时写态势报告。

## 2. 数据

| 表 | 作用 | 关键字段 |
|---|---|---|
| `watches` | 跟进卡本身 | `title`；`criteria`（城市、类型、方向、每周最多天数、只看大厂、关键词）；`status` active/paused/ended；`until` 截止日；`cadence_minutes` 检查间隔；`report_hour` 每天几点写报告；`notify` desktop/brief；`version` 条件每改一次加一；`baseline_at` 开卡时刻；`last_check_at`/`next_check_at`/`last_report_at`；`last_error` |
| `watch_targets` | 卡里的重点岗位和它们上次看到的样子 | `watch_id`、`job_id`（岗位被清理后置空）、`label`（岗位名，岗位没了也能显示）、`snapshot`（状态、城市、天数、时长、截止日、要求、JD 指纹）、`snapshot_at` |
| `watch_events` | 发现的每一件事 | `kind`；`importance` urgent/brief/quiet；`fingerprint`（同卡唯一，重复检查、重启都不会重复记）；`watch_version`；`ref`（J-/P-/Q-/R-）；`title`；`detail`（前后值、来源）；`notified_at`；`read_at` |
| `watch_reports` | 态势报告 | `period_start`/`period_end`；`facts`（报告依据的全部结构化事实）；`markdown`；`llm_call_id`；`fallback`（模型失败时用规则生成） |

都是新表，不改现有表。

## 3. 一次检查做什么（不调模型）

1. **重点岗位**：读当前字段，和 `snapshot` 逐项比：
   - 在招 → 下架：`job_closed`，紧急；
   - 下架 → 在招：`job_reopened`，进简报；
   - 每周天数、实习时长、城市、截止日、要求条目变了：`job_changed`，涉及本卡硬条件（天数、城市、类型）时紧急，否则进简报；
   - 岗位记录已被清理：`job_removed`，进简报（“库里没有了”不等于下架）。
   比完更新快照。
2. **范围内新岗位**：`first_seen_at` 晚于上次检查、且晚于开卡时刻的在招岗位，按卡的条件筛。用匹配规则看硬条件：没有明确冲突 → `new_job` 进简报，匹配分高且天数明确符合 → 紧急；有冲突 → 安静记录。
3. **范围内下架**：上次检查之后变成下架的范围内岗位 → `scope_closed`，进简报。
4. **新面经和题目**：范围内公司和方向的新面经帖、新题 → `new_material`，进简报。
5. **新的同类样本**：同方向、同公司的新求职者背景（拿到 offer 或挂了）→ `new_peer`，进简报。
6. **来源覆盖**：官网每日重采超过 36 小时没成功、登录平台今天被拒或限流 → `source_gap`，进简报，每个来源每天最多一条。**没查成不等于没变化。**
7. 没有任何事：只更新 `last_check_at`、`next_check_at`，不写事件、不调模型。

事件的 `fingerprint` 由“类型 + 对象 + 变化内容”组成，同一张卡里唯一：重复检查、进程重启后重跑，都不会产生第二条。

## 4. 提醒

- 紧急：Windows 通知（现有 `notify`），并出现在“今天”页的“需要你”；`notified_at` 记下，不重复发。
- 进简报：等每天的态势报告。
- 安静：只留在时间线里。
- 卡改了条件（`version` 加一）后，旧版本还没发的提醒不再发。

## 5. 态势报告（调一次模型）

每天 `report_hour` 之后第一次检查时写，或用户点“现在生成”。

**先用规则算出事实**，再让模型只根据这些事实写：

- 这段时间的事件（按紧急/简报分组，带编号）；
- 范围现状：在招岗位数、本期新增、本期下架、按公司分布；
- 硬门槛：范围内岗位因为什么把你挡在外面（要硕士、要每周 5 天……各多少个）；
- 技能需求：范围内岗位最常要求的技能、各占多少，哪些你的卡片里有、哪些没写；
- 同类样本：近半年同方向的自述样本，拿到 offer / 挂了各多少，学历、论文、实习写了多少；
- 你的进展：投递漏斗、被拒反馈；
- 覆盖：哪些来源这期没查成。

模型输出“发生了什么 / 对你意味着什么 / 你还差什么 / 建议这两天做什么”。之后校验：报告里出现的编号必须都在事实里；有不在的，换成规则生成的版本并标注。模型失败也用规则版本，不让报告断档。

## 6. 横向对照与 HR 视角（同一套事实，也给对话用）

- `profile_review` 工具：按一个范围（或一个岗位）给出
  - 资格：范围内岗位有多少因为哪条硬门槛和你冲突；
  - 技能覆盖：同上第 5 节；
  - 经历证据：卡片里的项目、实习；项目里写了 GitHub 链接的，只读取公开仓库的基本信息（最近提交、语言、有没有测试和 README）；
  - 可追问点：只列出“卡片里没写清的”，不替用户编。
- `peers_compare` 工具：按可比程度分三层（同公司同方向同类型 / 同方向同类型 / 同方向），每层给样本数、结果、学历、论文、实习的已知/未写数量，再和你的卡片逐项放在一起；每层不足 5 人就明说。学校只按帖子原话和常见说法（985、211、双非、海外）归类，不从学校名推测。

## 7. 接口

- API：`GET/POST /api/me/watches`、`GET/PATCH /api/me/watches/{id}`（改条件、暂停、恢复、结束）、`POST /api/me/watches/{id}/targets`、`POST .../check`、`POST .../report`、`POST .../events/read`。
- Agent 工具：`watch_status`（只读）；`watch_create`（会建一个长期运行的委托，要用户批准，和 `memory_forget` 一样走审批）；`profile_review`、`peers_compare`（只读）。
- 常驻采集每轮调用 `watch.run_due()`；网页“立即检查”直接调一次检查。

## 8. 合成演示

演示库没有采集。`python -m polaris.demo --advance` 每次按剧本改一点合成资料（重点岗位每周天数 4→5、一个岗位下架、出现一个新岗位、出现一篇新面经），再跑一次检查，演示跟进卡怎样发现变化、分级提醒和写报告。

## 9. 怎么验证

- 事件回放测试：无变化、天数变化、下架、重开、岗位被清理、新岗位（有/无冲突）、来源超时、重复检查、重启后重跑、改条件、暂停、过期结束、报告编号校验、模型失败回退。
- 合成演示网页走一遍；个人库建一张真实的卡跑一次检查和报告。

## 10. 刻意不做

- 不为每张卡单独提高采集频率：登录平台的配额不变；“检查”是读本地库的变化。云端高频直接查官网要等云端方案定下来。
- 不做任何对外发送；跟进消息仍只起草。
- 不爬个人主页；同类样本只用帖子里本人自述的公开内容。
