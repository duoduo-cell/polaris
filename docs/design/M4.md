# M4 设计：多来源对齐、知识图谱、混合检索

2026-10-11 实现（比排期 10-16 提前）。目标：把各来源的挂牌认成"同一个岗位"并裁决字段冲突（自己实现），把岗位、帖子、面试题建成能检索的知识层（关键词、向量、图谱三路加重排），用分开标注的标准答案量出同岗识别和检索的成绩。参考答案是腾讯 WeKnora（`REFERENCE_WEKNORA.md`），只借思路和参数起点，不用它的代码。

## 几个设计决定

- **标准答案按时间分三份，防止对着看过的例子调规则。** 同岗识别的开发集（80 对）调规则时看过；留出集（40 对）在第一版规则冻结后才标，第一版在上面只有 P=0.43、R=0.75，暴露出"同一官网同名不同岗"和"部门名只是字面包含"两类错，改成第二版；测试集（39 对）在第二版冻结后才标，只评不调：P=R=F1=0.93。测试集上的两处错（多语言 JD 漏并、"抖音研发中台"和"抖音研发"错并）留给下一轮，届时要再标新的测试集。
- **宁可少并，不错并。** 错并会制造假冲突：10-11 真实数据上唯一的字段冲突，恰好来自测试集里那对错并。所以同名岗位在同一来源要正文几乎逐字相同才并，部门名只是字面包含时要正文也像，帖子连到岗位要部门名和岗位名都对上。
- **冲突处理在真实数据上还没被充分检验。** 现在的真实岗位都来自各家官网，同一家只有一个来源；跨来源的冲突要等 Boss 的岗位接进来。目前的证据是合成数据（每个转载版故意改一个字段）10/10 发现、字段出处 100% 可追溯。
- **分词按我们的文本实测选。** 计划里写的是 lindera（WeKnora 用的），实测它把"评测""面经"拆成单字；jieba 保留这些词，还把"字节跳动"切成"字节/跳动"，搜简称也能命中。
- **查询扩展改成补公司别名。** pg_search 的 `|||` 本身按词"或"匹配，用 jieba 拆出变体没有增量；求职问题里真正的召回缺口是公司的各种叫法（字节、ByteDance、抖音），大厂名单里本来就有。
- **图谱一路只在有具体种子时召回。** 只命中"Agent"这类方向词时它会拉出几百个只沾边的岗位，所以种子总权重不到 1（至少一个公司、部门或技能）就不召回。单独看它最弱（NDCG 0.53），但加进融合后三路比两路高 0.02，擅长"腾讯要 RAG 的岗位"这类多条件同时满足的问题。
- **MMR 默认开。** 同一道面试题常被几篇帖子转载，NDCG 会把每份副本都算相关，所以加了"近重复率"指标：MMR 让前 10 的近重复率从 2.8% 降到 0.3%，NDCG 少 0.027。对用户来说，同一道题出现三遍是坏体验。
- **重排阈值按 qwen3-rerank 的分数分布重新定。** WeKnora 的 0.2 是别的模型的；qwen3-rerank 对不相关候选的中位数就有 0.49，阈值只能修掉尾巴，取 0.35（误伤 0 条完全相关）。
- **检索评测用 pooling 加 LLM 评审。** 32 个问题人写（含"想找什么"），7 种配置的前 20 汇成候选池，评审模型按 0/1/2 打分 1,395 条；开发 agent 抽查 40 条，三档一致 35、相关不相关一致 38，评审偏宽。评审结果含帖子编号，只放本机 `data/eval/`。
- **数据库换镜像不迁数据。** Docker Hub 拉不下 ParadeDB 镜像，就在原 pgvector 镜像上装它发布的 deb（同为 PG 17.11），原数据卷直接挂上，换前 `pg_dump` 备份。

## 结果

见 `../../eval/reports/M4.md`。要点：

- 同岗识别测试集 P=R=F1=0.93；合成冲突发现 10/10；字段出处可追溯 1,812/1,812。
- 检索 NDCG@10：BM25 0.732、向量 0.771、图谱 0.528、两路 0.784、三路 0.806、三路加重排 0.885、再加 MMR 0.858（近重复率 2.8% → 0.3%）。重排是最大的一步（+0.08）。分问题类型看，岗位类 BM25 强于向量（0.82 对 0.70），帖子类向量强得多（0.74 对 0.50），所以要融合。
- 完整流水线耗时中位数约 2 秒，几乎都花在两次网络调用（问题向量、重排）上；三路召回本身约 0.25 秒。
- 2,191 块全部算了向量（220 次调用、37.6 万 token、0 失败）；图谱 2,073 个节点、约 9,200 条关系，整图重建约 5 秒。
