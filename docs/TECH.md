原则（用户 2026-10-11 定）：
- 以自己开发为主；WeKnora 只做参考，不二次开发、不整体引入、不大段照搬代码。

- **记忆更新、多来源对齐和冲突处理、主动决策、评测闭环**这四处必须自己实现。
- 业务能力封装成自己的 MCP 服务。

2026-10-13 的研发侧重点、后续顺序和验证标准统一见 `PURPOSE.md`：**真实求职任务中的可靠工具调用与任务编排**。本文描述现有架构，不额外规定评测研发主线。

### 知识补跑候选契约（2026-10-21）

2026-10-22 运行修正：采集适配器在 Boss CLI 状态/只读请求前显式同步专用浏览器完整变化凭证（原子写CLI本地缓存，不控制Boss页面），防止CLI七天缓存覆盖新登录。`auth_status`保存搜索认证和原因；明确搜索失败不被其他认证字段覆盖。脉脉搜索等待commit后立即读额度响应，异常也检查登录/验证。`collect` Run零条目且有失败记failed，保留原始计数。官网最多3次恢复瞬态导航错误，拒绝/证书异常不重试。用户批准的-Bailian启动模式只给采集子进程设置百炼qwen-plus，来自既有设置，不改.env或网页模型；行为、回退和实测范围见 [采集修正记录](COLLECTION-2026-10-22.md)。下面知识维护契约的完成语义继续适用，Run146已含图谱成功不等于全量积压清空。

问题：知识处理失败后，旧逻辑主要靠新采集／抽取再次触发；没有新数据时可能一直不可检索。隔离反例已复现，当前实现为未部署候选，整轮验收未完成。实现见 `search/maintenance.py`，状态存既有 `runs`，不增加表、外部队列或依赖。

| 契约 | 候选行为 |
|---|---|
| 生产待办 | `run_extract()` 每条抽取结果与知识待办同事务；成功官网每日采集快照与待办同事务，即使没有新原文。待办保存失败则不提交该抽取／成功快照 |
| 合并通知 | 未完成任务增加 generation 并清除阶段检查点；保留冷却和失败次数。新数据不能绕过 exhausted；执行中的旧代不能把新代误标完成 |
| 执行顺序 | 对齐 → 切块／题目同步 → 向量 → 可选图谱。核心上游失败停止下游；同代已成功步骤可跳过 |
| 触发 | daemon 每个 `tick()` 在采集窗口、平台认证和浏览器判断之前处理到期待办；没有新增或不能采集时也可推进。需要 daemon 活着或人工执行，不承诺无人运行仍会恢复 |
| 有限重试 | 各核心阶段连续失败／中断初次加两次补跑，间隔至少 5 分钟；耗尽保留错误并等人工排队。下一次实际执行受 daemon 调度影响，5 分钟不是可用性 SLA |
| 工作量 | 一次维护最多处理 200 个向量块，成功但仍有积压则分多遍推进；成功会重置该步失败计数。对齐与切块仍全量，没有整遍硬时间上限 |
| 向量返回 | 验证 pending、embedded、failed_groups、remaining 为非负整数；局部失败、返回畸形、积压零进展不算完成。没有待向量块时不创建 LLM 客户端 |
| 向量写回 | 按块 ID、请求时正文指纹、当前仍待向量三个条件原子更新；旧正文结果、其他调用已完成和已删除记录不写入。embedded 计实际更新行数，remaining 重查数据库；不保证并发请求只调用模型一次 |
| 并发与退出 | PostgreSQL 会话 advisory lock 限制补跑 worker；短事务锁保护状态。网络／模型执行期间不持有数据库事务；进程直接退出后数据库释放会话锁 |
| 完成语义 | 核心处理检查点成功；不等于搜索质量或来源新鲜度合格。图谱禁用则跳过，图谱失败记 graph_error，核心 Run 可为 ok；核心完成后不自动补跑图谱 |
| 手工入口 | `knowledge-status` 只读；`knowledge-retry` 只把耗尽任务重新排队；`knowledge-work` 执行一遍到期待办，可能调用向量服务，不启动采集／浏览器。无待办时 work 不负责发现历史积压 |

为何选择：已有 PostgreSQL、Run、幂等切块和未完成向量查询足以承载这次故障；单查向量空缺不能表达对齐／切块失败，也不能限制失败次数。复用现有状态表比引入完整调度引擎更小，但需要自己维护领域阶段与完成语义。

执行保证是**至少一次**：副作用成功而检查点尚未提交时退出，步骤可能再执行，仍依赖原步骤幂等。coordinator 执行锁只限制维护 worker；下述独立派生写锁协调直接入口和 worker 的对齐／切块／题目写入，不是整条流水线串行锁。没有待办的历史失败／旧版本删除不自动扫描补齐；原文已保存但抽取未执行也不等于知识待办已产生。主动推送目前也不以核心完成为门槛。这些限制须按 PURPOSE 收拢，不能用本模块通过代替整链验收。

证据：隔离 `polaris_test`、合成数据、假模型／平台，覆盖子进程 `os._exit`、重启、局部批失败、200+5 分遍、generation 变化、耗尽和事务回滚；实际 pg_search 与 pgvector 查询分别验证可用。测试推进冷却时钟，不是真实等待或生产延迟；详细命令和未验证范围见 DEVLOG。

### 历史积压诊断与显式排队（2026-10-21，本地提交 112afd6，未部署）

实现为 `search/audit.py`，只读诊断与执行分开，不新增依赖／表。下表是现有候选契约，隔离通过不代表已允许对真实库恢复。

| 契约 | 行为与边界 |
|---|---|
| `knowledge-diagnose` | 不调用模型、浏览器或写库；单个 READ ONLY、REPEATABLE READ 事务；每条 SQL 30 秒期限，非整次硬期限。返回 snapshot_at、elapsed_ms，不输出原文，不加载向量 |
| 状态与数据 | task 只表示最新维护任务；raw_pending 分 job/post 数量及最早时间，不计为知识 worker 待办。needs_refresh 仅表示本次已检查的对齐、块、题目或向量存在缺口 |
| 对齐／切块／题目 | 复用 alignment_rows、build_chunks、chunk_values 和纯 profile 规则。报告缺失／变化／过时及关联缺口；不调用会写入的 sync_questions。日期及等价时区规范比较 |
| 元数据同步 | `_sync_chunks` 比较全部持久业务字段，元数据改变也更新，保留 embedding 和 embedded_hash；正文指纹不变无需重嵌入。日期映射为 UTC 零点，非采集时间 |
| 待向量条件 | `embedding IS NULL OR embedded_hash IS DISTINCT FROM content_hash`；诊断、选取、原子条件写回和剩余统计共享；正文版本保护继续生效 |
| `knowledge-enqueue` | 先诊断，再在维护状态锁内判断；耗尽不复位，活跃任务不清检查点或冷却，无已检出积压则不排。blocked 可重新诊断排队，保留失败次数；仅登记待办，不立即执行 |
| 清理范围 | NULL key 始终不自动清理，另报 unmanaged_jobs。存在受管理岗位而对齐输入为空时，排队与执行都拒绝；任何候选含人工跟进／事件也拒绝，许可不能覆盖 |
| 清理许可 | `--allow-prune` 保存本次诊断候选 ID → SHA-256 到 Run.params.prune_approval。指纹含 Job 全列（除 embedding）及关联 Posting ID 集合；新 generation 清除此许可，不向新代继承 |
| 执行保护 | 对齐在 upsert 前对候选按 ID 取 FOR UPDATE，再查人工记录及指纹；仅删除已锁定、未变化且获许可的固定 ID，可缩小不可扩大。任一候选受阻整体回滚，不继续切块／向量 |
| 受阻与恢复 | worker 保存 blocked_reason/count/at，撤回本次 claim 计数，保留旧失败次数及新代待办；新通知和通用 retry 不解锁。重新诊断可恢复合法清理；不自动迁移人工记录 |
| 尚无保证 | 许可不是全库、所有原文或跨阶段快照；关联 Posting ID 指纹不验证其全部正文。worker 清理以 Run FOR SHARE 检查代次，与通知 UPDATE 串行；通知先提交则旧许可拒绝，清理先核验则通知等其提交后登记新代，旧代不能完成新代。整链延迟、真实任务和部署仍未验收，不对真实库运行恢复 |

诊断全量扫描，不能证明抽取质量、提示词／模型版本兼容、来源真实性、向量数值质量、图谱健康或实际召回。快照后数据可变化；诊断无缺口不是整库健康证明。最新清理及相邻集合 136 项隔离通过、0 跳过，命令见 DEVLOG。并发跟进先提交则清理被阻止；清理已持父行锁时，晚到保存会等待并可能明确外键失败，不保证两者同时成功。

### 派生知识并发边界（2026-10-21，候选隔离通过，未部署）

`tests/test_knowledge_consistency.py` 原 5 项失败现已转绿：全量切块旧快照覆盖全量／指定帖子新结果（2 项）、旧对齐清理新岗位（1 项）、题目先提交使切块失败不能整体回滚（1 项）、指定帖子同步使用 caller Session 旧对象（1 项）。该文件现有 13 项；与诊断、向量、维护、daemon、search、align、results、jobs_tools 共 117 项通过、0 跳过，4 条既有弃用告警。使用隔离 PostgreSQL、合成数据和假服务，无真实模型／平台。

实现为 `search/locking.py`，复用 PostgreSQL，不新增依赖、表或迁移：

| 契约 | 行为与边界 |
|---|---|
| 参与入口 | `run_align`、`sync_chunks`、`sync_post_chunks`、独立 `sync_questions` 在读取／派生前申请事务 advisory lock `2026102103`；之后才取 Post 行锁。指定帖子入口本次未发现生产调用方，不能宣称已接通在线修复 |
| 事务范围 | 对齐读取／构造／写回／清理在同一 Session；全量切块的题目、画像、构块及写回同事务，任一失败整体回滚。不把不同阶段或所有原文读取变成一张全局快照 |
| 调用方 Session | 申请锁使用 `no_autoflush`，锁忙时不先保存脏对象；成功后显式 flush，再用 `populate_existing` 重读，保留合法未提交修改。提交／异常回滚由调用方负责；忙后应结束本事务并重新读取后重试 |
| 竞争结果 | `pg_try_advisory_xact_lock` 忙时立即抛 `KnowledgeWriteBusy`。worker 只撤回本次 claim 增量、保留既有失败额度与新代次，记录 `waiting_for=knowledge_writer`，5 分钟后再尝试；持续竞争没有完成时限保证 |
| 直接刷新 | `refresh()` 上游异常后停止下游；忙时返回 `retryable=true`。它不会自动保存待办或重试；手工 align/index 的忙异常由调用者处理 |
| 向量 | 网络请求仍在数据库事务外；沿用正文指纹与当前待处理条件写回，未串行化网络调用 |
| 未保证 | 仅协调遵守协议的派生入口；原文、抽取和原生 SQL 写入不全参与。清理执行保护见上表；整链延迟及真实任务仍待验收，没有性能提升证据 |

本轮补充验证发现 Session.scalar 自动 flush 会发生在锁忙判定前；`no_autoflush` 后反例通过。事务锁在事务结束释放；不在模型／网络等待期间持有它。具体通俗解释见 DEVELOPMENT 第 6 节，路线仍由 PURPOSE 维护。

## 1. 总体架构

```
你的电脑（要登录的平台，B 档）                         Polaris Core（FastAPI，同一个 Python 进程族）
┌──────────────────────────────┐                     ┌──────────────────────────────────────────┐
│ 采集专用 Edge（小红书、脉脉）   │◀─Playwright CDP──┤ 常驻采集进程（配额、遇阻即停、日报）        │
│ Boss 专用 Edge（不被程序接管）  │◀─boss-cli 取 cookie─┤ 抽取（结构化输出、校验重试）               │
└──────────────────────────────┘                     │ LangGraph 主 agent、侦察流程、人工审批       │
公开来源（A 档，可上云）：腾讯接口、字节和小红书官网 ────▶│ 检索：关键词 + 向量 + 图谱 → RRF → 重排     │
                                                      │ MCP 服务（只读工具 + 需审批的工具）          │
                                                      └───────────────┬──────────────────────────┘
                                                                      │
                          ┌───────────────────────────────────────────┼──────────────────────┐
                          ▼                                           ▼                      ▼
      Postgres 17（ParadeDB 镜像）                        Neo4j 5.26 社区版 + APOC        前端 Next.js
      业务数据、原文、pgvector 向量、pg_search BM25        知识图谱（可关）                 （Vercel AI SDK）
      记忆、检查点、调用追踪
```

**默认只依赖一个 Postgres**，Neo4j 是可关的组件（关掉时图谱这一路召回为空，其他照常）。
聊天使用 Postgres 持久化任务队列；不引入 Redis 或独立消息队列。常驻采集由独立进程循环执行，配额和锁共用。
工程师子 agent 和独立审查角色是规划项，不能当作已实现的运行节点。

## 3. 十个环节

| 环节 | 方案 | 自己写 / 现成 / 参考 | 指标 |
|---|---|---|---|
| 1. 信息采集 | 侦察子 agent 按来源并行；每天和每小时配额、慢启动、遇阻即停；原文入库带发布时间、首末次采到、近似重复指纹 | 自己写 | 每天新增、限流次数（目标 0） |
| 2. 信息抽取 | 结构化输出加校验重试；提示词版本化，先开发集再留出集 | 自己写 | 逐字段 F1（已有） |
| 3. 去重、对齐、冲突 | 同岗判定（`align/match.py`）：同公司、部门逐段相容、岗位名一致或几乎一致且差异里没有区分词（研发/算法/高级…）、正文不矛盾（同一来源比三元组 Jaccard，跨来源比 SimHash）；完全链接聚类，不串联。字段裁决（`align/resolve.py`）：来源可信度加权投票，平分取最近采到，发布日期取最早，城市取并集，落败值和出处全留；官网快照推断下架（待做） | **自己写** | 同岗识别 P/R/F1（开发集、留出集、测试集分开报）；冲突发现率；出处完整率。10-11：测试集 P=R=F1=0.93 |
| 4. 知识存储 | Postgres 存事实和原文；Neo4j 存图：公司、事业群、团队、岗位、城市、方向、帖子、面试题，每条边带来源和时间；APOC 幂等写入 | 结构和写入自己写；写法参考 WeKnora | 实体合并 P/R |
| 5. 卡片和记忆 | 双时间线事实表；新增、更新、作废、不变；推断的先进"待确认"，被拒绝的留抑制记录；矛盾时追问；对话摘要压缩后整合进卡片 | **自己写**；"待确认、抑制记录"参考 WeKnora | LongMemEval 式五项 |
| 6. 匹配、检索、主动决策 | 检索流水线见第 4 节；推送打分（新颖度、匹配度、紧迫度）、时机、克制 | 检索编排自己写、参数参考 WeKnora；**主动决策自己写** | Recall@k、NDCG@3/@10、MRR、MAP；推送准确率、漏报率、打扰率 |
| 7. Agent 编排 | 主 agent 唯一写入；侦察、审查、守门、工程师；规则见第 5 节 | LangGraph 现成，规则参考 WeKnora | "模拟一天" pass^3 |
| 8. 行动和工具 | 业务能力封装成自己的 MCP 服务；工具分只读和有副作用；有副作用的按策略表审批 | 自己写 | 未经批准的对外动作为 0 |
| 9. 对话和上下文 | 分块见第 4 节；卡片常驻上下文，事实按问题召回；对话长了摘要压缩 | 分块参考 WeKnora；压缩用 LangChain 中间件 | 压缩前后正确率之差、省下的 token |
| 10. 评测、追踪、反馈 | 标准答案集、逐字段打分、工具调用套件 pass^k、录制回放、故障注入、检索指标、CI 回归；你的"有用"反馈 | **自己写** | 见各模块报告 |

## 4. 检索和分块

**分块**（参考 WeKnora `04-chunking.md`，按我们的短文本简化）：
- 每块前面加上下文头：岗位写"公司 ｜ 事业群 ｜ 岗位名 ｜ 职责或要求"，帖子写"来源 ｜ 涉及公司 ｜ 类型 ｜ 日期"。
- 岗位：职责、要求分开成块。
- 帖子：不到约 1,500 字的整篇一块；更长的用父子分块（子块检索、整帖回答）。
- 面经里的每道面试题单独成块，挂在原帖下面。
- 不做通用文件解析服务。小红书截图已有 OCR：读取文字后只在本机保存，和正文、评论分开；
  图片题目可以提供正文证据，评论中的公司不继承为面试公司。

**人和结果工具（10-12）**：`peer_profiles` 保存帖子里的自述背景、阶段、目标、结果、日期和原句，
`peers_search` 按公司、方向、阶段、结果和最近天数筛选，并在工具返回中去重。
未提实习和明确没有实习分别返回、分别计数；样本不足时不能推出普遍门槛。
面试题的轮次按原句位置和题目分组标题确定，时间线中的“一面、二面”不能自动分配给后面所有截图题目。

**检索流水线**（参考 WeKnora `04-rag-pipeline.md`，默认参数作起点，再用我们的标准答案集调）：

| 步骤 | 做法 | 起始参数 |
|---|---|---|
| 1. 问题理解 | 抽出结构化条件（公司、城市、类型、时间）和实体名；闲聊不检索 | — |
| 2. 结构化过滤 | 按条件在 Postgres 里先筛 | — |
| 3. 三路并行召回 | 关键词：`pg_search` BM25（jieba）；向量：pgvector（HNSW，带过滤时迭代扫描）；图谱：问题里的公司、部门、技能、城市、方向 → Neo4j 一跳邻居 → 关联的岗位、帖子、面试题，连到的种子越多越具体排越前；只有宽泛种子时不召回 | 向量阈值 0.15，关键词为第一名的 0.3 倍；图谱种子权重部门 2、公司和技能 1、城市和方向 0.5，种子 ≤ 200、行 ≤ 2000、并入 ≤ 30 个文档 |
| 4. 查询扩展 | 关键词召回少于 5 条时，把问题里的大厂补上它的各种叫法（字节 → 字节跳动、ByteDance、抖音……），只加在关键词一路。原计划用 jieba 生成变体，但 `|||` 本身就按词"或"匹配，拆词变体没有增量 | 关键词阈值放宽到 0.8 倍 |
| 5. 融合 | 加权 RRF，归一到 0 到 1 | k=60，向量 0.7、关键词 0.3、图谱 0.3 |
| 6. 重排 | qwen3-rerank；最多 50 条；低于阈值时保底留第一名；重排失败退回融合分 | 阈值 0.35，保底 0.25（按 qwen3-rerank 的分数分布标定，见 `eval/reports/M4.md`） |
| 7. 综合分 | 0.6×重排分 + 0.3×融合分 + 0.1×来源权重 | 岗位 1.0，帖子 0.9 |
| 8. 去冗余 | MMR，冗余度用分词后的 Jaccard | λ=0.7 |
| 9. 截断 | 分数相同按编号排，结果可复现 | top 10 |

## 5. Agent 规则

### 已实现的聊天、上下文和任务分离（10-11）

- **展示记录**：`chat_messages` 仅保存用户原话和正式回复（包括最终的记忆确认追问），不从 LangGraph 最新检查点生成；
  `chat_threads` 保存导入标记和待审批状态。旧会话首次打开时遍历保留的历史检查点，以消息 ID 去重，过滤摘要标记和带工具调用的 AI 消息。
  已被清理的旧检查点无法恢复；之后的上下文压缩不会改写展示记录。
- **模型上下文**：仍使用 LangGraph Postgres 检查点、LangChain 摘要中间件、记忆卡片和检索结果。内部摘要只供模型使用。
- **任务与活动**：`chat_tasks` 持久保存输入、队列状态、工具/记忆活动、结果、错误和时间。网页提交后获得任务 ID，
  每秒查询进行中的任务，空闲时每五秒同步；刷新、关页、网络断开不取消执行。
- 调度器通过 PostgreSQL 会话锁选出一个执行者，最多同时处理四个不同会话；同一会话串行，最多排队 20 条。
  共享记忆通过事务锁保证单次写入，避免并行对话写出重复事实。请求 UUID 幂等，审批决定也只能生效一次。
- 后端意外重启：运行中的任务标记中断，不自动重放；已进入审批检查点的恢复为待审批，排队任务继续。
  当前是本机后端持续运行期间的后台任务，没有承诺断电后的模型调用能无缝续跑。
- 网页保留现有外观，只显示自然语言进度和正式回复，记忆/工具参数放进默认收起的活动记录。
  为避免工具调用前的套话混入正式回复，确认模型消息不含工具调用后才发布其文字。
- 新接口：`POST /api/me/chat/tasks`、`POST /api/me/chat/{thread}/resume/tasks`（均需 `request_id`），
  `GET /api/me/chat/tasks/{id}`、`GET /api/me/chat/threads`、`GET /api/me/chat/{thread}/messages`。
  全部沿用 OWNER_TOKEN；旧同步/SSE 接口也通过持久化队列执行。

依据：本机安装的 LangChain `SummarizationMiddleware._build_new_messages` 用带 `lc_source=summarization` 的 HumanMessage 替换旧上下文，
因此其角色不能等同于用户发言。产品层的后台任务、长对话和折叠活动参考
[Muse 的设计说明](https://introducing.muse.ai/)、
[Dots 任务与记忆](https://learn.chatgpt.com/docs/dots/tasks-and-memory)；具体保证由本项目的断连、压缩、审批和并发回归验证。

参考 WeKnora `07-agent.md`、`08-mcp.md`：
- 一轮里多个工具调用：只读工具并行，有副作用的串行。
- 单个工具 60 秒超时；到轮数上限时带着已有结果、**不带工具**再调一次模型收尾。
- 给模型看短编号（J-12、P-3、R-7），不给内部 ID（已有）。
- 有副作用的工具按策略表审批：批准、拒绝、改参数（改后重新按 schema 校验）；默认等 10 分钟；拒绝和超时作为工具结果交还 agent。用 LangChain 的人工审批中间件实现，策略表存在 Postgres。
- 小红书、脉脉、Boss 的原文进上下文前加"不可信"标记，守门 agent 也看这个标记。
- MCP 服务：口令（已有）、工具白名单、限流。

## 6. 评测和追踪

- **当前验证规范**见 `PURPOSE.md`。保留模块回归和完整追踪，用真实失败驱动对照；裁判只辅助，不以扩建评分器为研发主线。录制回放验证代码回归，真实模型重复运行才验证决策波动。
- **检索评测**参考 WeKnora：qrels 形式的标准答案（问题 → 相关条目编号），算 Recall@k、NDCG@3/@10、MRR、MAP，中文用 jieba 分词。回答质量不用 BLEU、ROUGE。
- **追踪**：`runs`（一次运行）、`tool_calls`（一步）、`llm_calls`（一次模型调用）对应 Trace、Span、Generation 三层；每次调用记 token、耗时、费用。

## 8. 风险和备选

| 风险 | 备选 |
|---|---|
| ParadeDB 的中文分词效果不够 | 加一列 jieba 预分词的文本再建 BM25 索引 |
| Neo4j 在 2 核 4G 云主机上太占内存 | 云端关掉图谱（可关的设计），图谱只在本机跑 |
| 某个平台的单账号额度太低 | 降配额、换不用登录的来源补（官网、牛客） |
| 开发期模型思考关不掉，耗时和 token 偏高 | 评测时缓存模型输出；正式数字在提交用的模型上出 |
| LangSmith 在国内网络连不上 | 只用自有追踪表 |

### 10-12 结果展示与证据补充

- `GET /api/me/results/{J/P/Q-id}` 直接提供详情和安全原始 URL；`GET /api/me/knowledge/posts`、`questions` 提供不调用模型的筛选分页。全部沿用 owner 鉴权。旧聊天首次读取时验证历史成功工具出处，补保存展示数据。
- `interview_questions` 按 `post:{id}:q{index}` 幂等保存题目、正文公司/岗位/轮次/类别、材料性质、证据和两个日期；`posts.evidence_profile` 记录正文/评论公司与修复版本。`ASKED_AT` 只使用明确归属的面经题，发布时间不能替代面试日期；旧向量仅在 embedded_hash 与 content_hash 一致时可用。
- `job_followups` 按 job_id 独立保存收藏、状态、面试阶段、备注和日期；`job_followup_events` 保存前后值及用户来源。明确 UI 操作使用 UUID 去重和 revision 冲突保护，沿用共享记忆写锁；阅读/收藏不推断投递。自然语言按明确编号、完整岗位名、推荐序号或唯一已投岗位解析范围，有多个可能时先追问，推断不写入已投递状态。
- 迁移只增加结构，不清空聊天、记忆、原始资料。存量证据/块/图谱回填不调用模型；不运行 drop_stale 或批量重抽。备份与原始内容留在忽略目录，公开版本不含真实帖子。

- 指定帖子同步入口 `sync_post_chunks(session, post_ids, skip_locked=True)`：先取共享派生写锁，再按帖锁住抽取行；同一事务同步题目和检索块，只删该帖失效的条目。共享锁忙抛待重试，行锁忙可跳过；岗位与其他帖子保持完整。正文哈希变化的块随后重算向量，旧向量不参与检索。本次未发现生产调用方，不能称在线修复已接通。
- `peers_search` 明确返回查询时间、人群范围和未知学历/论文数量；`job_type=实习` 只含日常与暑期，默认只查明确大厂。不同查询可能重叠，不能叠加计人数；查 offer 背景必须单独筛结果。后台记忆缺字段不能视为用户没有经历，也不能由背景推断用户答不出题。
- 明示“并非全部为本人亲历”的清单划为备考整理；粉丝/读者/网友投稿划为待核实。公司和题目筛选遵守材料性质，不能把投稿包装成作者亲历。
