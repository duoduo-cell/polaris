# 北极星整体开发手册：从发现问题到可核实作品

适用对象：项目作者与协作开发助手。更新日期：2026-10-21。

这份手册解释“怎么做开发、怎么判断做得好不好”。目标、优先级和下一轮顺序只在 [PURPOSE](PURPOSE.md) 维护；实际完成状态看 [STATUS](STATUS.md)，开发过程只记 [DEVLOG](DEVLOG.md)。本文件中的任务和验收样例不是已完成成果。

## 先读这一页：你可以怎样理解整个开发

**我们先让一件求职任务做对，再让它遇到故障时可控，测过以后再优化和增加能力。** 你不用先学会全部框架；先看每一轮能否清楚回答：“哪里有问题、为什么改、怎样证明改好了”。

整个过程反复走这一条线：

> 收集真实问题 → 把同类问题放在一起 → 找到可复现原因 → 设计一个最小改动 → 验证结果、过程和保存状态 → 决定保留或撤回 → 再看下一个问题。

| 你想知道的事 | 直接看哪里 |
|---|---|
| 现在到底做什么、为什么先做它 | [PURPOSE 的三轮执行卡](PURPOSE.md#接下来三轮的执行卡计划未验收) |
| 什么已经做了，什么还没通过 | [STATUS](STATUS.md)；“写了代码”“测试通过”“已启用”分开看 |
| 我怎样找问题、改代码、验收 | 本手册第 3–8 节 |
| 我每轮应该交给你什么 | 本手册第 12 节的汇报模板 |
| 怎么把开发变成面试能讲的材料 | 本手册第 13 节 |

每轮至少交付四样东西：**一个失败案例、一份简短设计、一组前后验证、一段你能讲清的工程解释**。未通过的项目和原因一起交付；不是写完代码就结束。任务复杂时先交付可验证的小步，不把所有功能一起改完才汇报。

你只需判断结果是否符合求职需要，并逐步理解一个核心机制。案例准备、资料查证、代码排查和隔离验证由我负责；账号或权限确实阻塞时，我再给你最小必要操作。

### 不懂技术时，先用这张执行总表

**发展方向保持：可靠工具调用与任务编排；辅助关注证据和时间。** 开发围绕一条求职任务逐层深入：先做对，再经得住失败，再减少浪费，最后才按真实需要增强。当前具体排期只看 PURPOSE 的三轮卡。

| 关口 | 我应该提出的问题 | 我必须交出的东西 | 什么情况下继续 |
|---|---|---|---|
| 发现 | 你本来要做什么，哪里没有做到？ | 一个具体请求、实际结果、正确结果 | 能说明影响；纯猜测先记录待查 |
| 定位 | 第一处错误出在哪里？同类现象是否同因？ | 可复现案例、正常对照、已证实原因与假设 | 确定输入直接测试，分清模型、接口、数据和展示 |
| 设计 | 最小改动是什么，现有组件为什么不够？ | 一页设计卡：行为、边界、替代方案、代价、回退 | 有可验证标准，再动实现 |
| 修复 | 原案例和同类案例都改对了吗？ | 代码差异、实际状态、反例及相邻回归结果 | 失败项如实保留，未通过不报完成 |
| 优化 | 当前什么最费时间或调用，测量依据是什么？ | 同条件前后记录及未改善项 | 正确性不下降，节省有实测依据 |
| 增强 | 哪个真实请求现有机制完成不了？ | 新请求、最小实验、收益与新增维护负担 | 预留请求也有效；无收益就暂停或撤回 |
| 交付 | 作者和别人实际能用吗？ | 完整任务记录、合成演示、干净启动、局限 | 网页、工具、回答及保存状态一起核对 |

你不需要先给出技术方案。每轮只需看三件事：**原来哪里错、现在凭什么说好了、还有什么没保证**。修复失败可以成为有价值的发现，但不能包装成升级成功。

当前取舍：保留现有采集、检索、记忆与图谱；深化工具契约、有限重试、版本一致性和完整任务验收；暂停扩平台、换框架和通用多 Agent 平台。事务、数据库、模型 SDK、执行框架优先复用，领域状态和完成标准由我们自己负责。具体分工见第 9 节，外部依据见第 10 节。

### 如果你现在只想知道“接下来怎么做”

先打开 [PURPOSE 的三轮执行卡](PURPOSE.md#接下来三轮的执行卡计划未验收)，每次只执行当前一轮。每轮我先交代失败和证据，再解释设计，再开发验证，最后告诉你哪些通过、哪些仍不能保证。路线顺序在 PURPOSE 更新，这里不另维护一套待办。

你可以直接用下面四句话检查我的工作，不需要懂代码：

1. **请把改之前失败的例子给我看。** 如果只有“应该更先进”，先不给它排开发优先级。
2. **请说明它属于哪类问题，为什么不是另一类。** 例如搜不到，必须分清没数据、没处理完、条件不符和调用失败。
3. **请用同样条件证明改后行为，并告诉我哪些没测。** 假接口通过、真实模型通过、网页验收、正在运行要分别回答。
4. **请说明我实际少做了什么，以及新增了什么维护负担。** 暂时没有效果数据就保留待验证，不用测试数量代替用户收益。

每轮结束时，我会给出“保留／继续定位／撤回”的建议及依据。你不需要逐条批准排查命令；已有授权范围内的工作由我推进，产品取舍需要你判断时给你具体结果。未经确认的对外动作、账号操作和运行切换继续遵守项目边界。

### 整体开发会怎样逐步变深

| 顺序 | 你会看到的变化 | 我必须先回答的问题 | 进入下一步的门槛 |
|---|---|---|---|
| 先把任务做对 | 条件不串、未知不乱猜、保存有依据 | 第一处错误在哪里，确定输入能否复现？ | 原反例与正常对照都过；未验证范围列明 |
| 再把失败管住 | 超时能停止、失败能看见、必要工作能有限补跑 | 哪些可以重试，重复做有什么后果？ | 无新增、重启、局部失败、耗尽都受控 |
| 然后减少浪费 | 少做重复调用、少等无用查询 | 现在的实际瓶颈是什么？ | 同条件正确性不退步，时间或调用量确有减少 |
| 最后按需增强 | 需要时再加入证据回读或有限恢复 | 现有能力为什么不能满足真实请求？ | 在预留请求上有收益，复杂度可以承担 |
| 贯穿交付与自用 | 别人能打开，自己能持续发现问题 | 干净环境能否运行，实际省了什么工作？ | 演示、复现说明、反馈与局限能互相核对 |

这是开发门槛，不是五条同时开工的功能线。当前三轮的具体安排仍只看 PURPOSE；不因为测试数量增加就自动进入增强阶段。

## 1. 先知道我们到底在做什么

北极星面向中国 LLM / Agent 实习求职者，让作者自己能完成：

> 按本次条件找岗位 → 核验来源与时间 → 解释符合、不符、未知 → 根据选中的岗位准备面试 → 保存自己确认的跟进。

主方向是**可靠工具调用与任务编排**。用普通话说，就是程序知道该查什么、查到的能不能信、失败后怎么办、什么时候停止，以及最后有没有真正完成你的要求。辅助侧重是证据和时间语义：每个重要结论从哪里来、说的是哪个时间。

已有检索、记忆、图谱、工具与任务存储应继续使用；后续工作围绕这条完整任务修补和验证。适合证明 Agent 应用／后端工程能力；不能据此宣称具备训练、SFT 或 RL 经验，也不能保证招聘方认可。

### 你需要理解的几个词

| 词 | 在北极星里的意思 |
|---|---|
| 工具 | 程序提供的动作，例如查岗位、打开来源、读记忆；模型选择调用，程序负责执行 |
| 编排 | 决定先做什么、是否补查、可否并行、何时停止 |
| 契约 | 调用双方对输入和结果含义的约定；例如“未知”不能解释成“关闭” |
| 轨迹 | 一次任务每一步的工具、参数、结果、错误和用时记录 |
| 幂等 | 相同操作重复执行，不造成重复记录或重复副作用 |
| 回归测试 | 改动之后重新检查以前能做对的事情，防止修好一处、弄坏另一处 |
| 端到端验收 | 从网页发出请求，一直核对工具、回答、卡片和保存结果 |
| 留出请求 | 修改前留一批暂不用于调试的新请求；看过并用于修改后就转成回归材料 |

## 2. 从哪里出发：当前能力和缺口

以下是 2026-10-21 文档及代码核对快照，后续变化查 STATUS，不在这里重复维护进度。

| 项目 | 当前事实 | 后续要证明什么 |
|---|---|---|
| 基础流程 | M0–M7 已有实现，不能从零重做 | 一次完整任务能否稳定完成 |
| 来源核验 | 工作区候选区分页面可读、明确关闭、无法核验，定向回归通过 | 真实任务中解释正确；页面可读不能说成仍在招聘 |
| 采集与补处理 | 官网成功状态、失败冷却、无新增时补处理已有候选；知识补跑也已有候选与隔离测试 | 历史未排队积压、直接刷新并发边界、真实任务和实际可用延迟仍待完成验收 |
| 条件和卡片 | 查询条件与默认长期画像存在不同路径；前端已有未提交改动 | 是否造成误导，不能仅凭路径不同就认定实站出错 |
| 任务持久化 | 能保存任务；重启后可标记中断或待审批 | 不等于所有任务自动无缝续跑 |
| 演示与交付 | 独立合成演示和干净启动未完成 | 别人能运行、能体验、能核实且不接触真实数据 |

已有候选未部署，模块测试通过不等于整体验收通过。最近保存的采集运行快照不能证明当前持续在线；每次运行判断都要注明核查时间。

## 3. 我怎样提出一个值得解决的问题

先描述用户受到什么影响，再找原因。每个问题必须回答六句话：

1. **你当时要完成什么？** 例如“找上海、每周三天的 Agent 实习”。
2. **实际发生了什么？** 例如“卡片仍按北京偏好判断”。
3. **正确行为是什么？** 例如“按本次上海条件解释，不修改长期偏好”。
4. **证据在哪里？** 原请求、工具参数和返回、卡片、数据库记录、版本。
5. **影响多大？** 会错过岗位、浪费核查时间，还是只是表达不清？
6. **怎样复现和验收？** 给一个最小案例，并写出可以检查的结果。

“换一个更强模型”“加个多 Agent”“优化接口”都是方案或愿望，不能直接代替问题。无法复现时先标记待定位，不提前给根因下结论。

### 我会主动准备哪些问题

| 类型 | 示例请求或受控条件 | 检查什么 |
|---|---|---|
| 正常找岗 | 找上海 Agent 实习，不足三条就如实说 | 有依据、不凑数、不遗漏已知硬冲突 |
| 条件变化 | 长期想北京，这次只看上海 | 工具、回答、卡片一致，长期偏好不被误改 |
| 信息缺失 | 岗位没写每周到岗天数 | 标为待确认，不能当作符合或不符 |
| 明确冲突 | 合成岗位明确要求硕士，合成人物为本科 | 不用高匹配分抵消硬冲突 |
| 时间问题 | 最近七天发布的面经、现在还能访问的岗位 | 区分采集时间、发布时间、面试时间、核验时间 |
| 零结果 | 合成库中确实没有符合条件的岗位 | 解释当前范围，不推断全平台无岗，不擅自放宽条件 |
| 数据未就绪 | 已有原文，受控地使索引失败 | 不把未处理当无岗位；恢复后实际能查到 |
| 外部故障 | 假接口返回超时、429、403、加载页 | 原因明确、有限停止、不误报关闭 |
| 重复／中断 | 重复请求标识、取消、在隔离服务重启 | 不重复生效，完成与未完成状态诚实 |
| 连续任务 | 选岗后准备面试，再保存确认的跟进 | 岗位归属正确、证据可回看、保存动作符合确认 |

初始准备 12–20 个任务覆盖主要类型。故障注入是用假接口制造失败，先不影响真实采集。真实自用问题优先；我生成的补充题会标注来源，不冒充真实用户反馈。任务数量用来控制工作量，不能据此宣称统计充分。

### 可以直接照着执行的首批 16 个验收题

下面是**验收设计，尚未作为这一整组执行**，不是新增功能清单，也不改变 PURPOSE 的迭代顺序。案例由我准备：优先整理已有自用记录，其余使用标注清楚的合成条件；这里的城市、学历和天数均为测试条件，不代表作者真实背景。每题至少保存请求、版本、工具参数和结果、预期与实际行为；涉及保存的还要查数据库。

| 编号与分组 | 我准备的请求／受控情境 | 什么才算通过 | 失败后先查哪里 |
|---|---|---|---|
| A1 数据可用 | 合成岗位已入库，向量服务首次返回局部失败，之后没有新数据 | 失败不计完成；到期后继续处理，实际向量查询能找到；正常块不重复生成向量 | 待办是否保存、阶段结果、实际剩余块 |
| A2 数据可用 | 在隔离进程处理中途退出，再启动隔离 worker | 必要待办仍在；已完成与待处理可区分；没有重复业务记录 | 提交边界、检查点、锁释放及重复执行 |
| A3 数据可用 | 历史数据未排队，维护状态为 idle 或旧任务为 ok | 诊断能指出已检查范围和缺口；不能据此报告全库健康；恢复入口的设计需另行验收 | 任务状态与真实数据积压是否被混用 |
| A4 数据可用 | 核心阶段持续失败达到额度，再有新数据通知 | 保留耗尽与失败原因，不因新通知无限重置；人工恢复有明确边界 | 失败计数、代次、人工重试条件 |
| A5 并发一致 | 老正文的向量请求尚未返回，新正文已生成向量，老请求才返回 | 新向量保留；完成数按实际写入计；实际查询仍可用 | 写回的版本条件和数据库持久状态 |
| A6 来源语义 | 假来源依次给加载页、“该职位已更新”、明确关闭、429 和超时 | 加载／故障保留未知，更新不等于关闭；可读不等于仍在招；工具和回答口径一致 | 来源解析、返回契约、Agent 解释 |
| B1 条件贯穿 | 合成长期偏好北京，请求“这次只看上海” | 工具、回答、卡片按本次条件；长期记忆未改 | 当前条件进入工具及卡片的路径 |
| B2 条件贯穿 | “每周三天”，岗位没写到岗天数 | 标待确认，不冒充满足或明确不符 | 缺失值、匹配解释、卡片展示 |
| B3 条件贯穿 | 合成本科背景，岗位明确要求硕士，其余条件很好 | 明示硬冲突，排序分不能覆盖冲突 | 硬条件判定及前后端含义 |
| B4 空结果 | 合成库没有符合条件的岗位 | 如实说明当前查询范围；不凑数、不放宽硬条件、不推断全平台无岗 | 检索条件、补查与停止依据 |
| B5 空结果 | 确认库中有符合条目，使用几种自然表达询问 | 检查是否找到该条目；找不到时区分索引、召回、过滤和模型决策 | 同条件直接调用工具与原任务的差异 |
| B6 时间语义 | 固定时钟，面经发布时间在七天内、采集时间不同、面试发生更早 | 按请求的时间字段筛选并说明；字段未知如实保留 | 日期提取、字段来源、工具参数 |
| C1 连续任务 | 找岗后指定其中一岗准备面试，再确认保存跟进 | 岗位归属和引用正确；只保存确认内容，实际落库 | 选中实体、证据关联、写入事务 |
| C2 重复与取消 | 相同请求标识重复提交；另一次任务执行时取消 | 不重复产生该请求的任务／写入；取消状态如实显示，不把部分完成说成全撤销 | 请求去重、执行次数、实际副作用 |
| C3 停止边界 | 假工具连续失败或反复返回相同空结果 | 达到规定预算后停止；说明已完成、失败及可继续条件 | 重复调用保护、总预算和单步超时 |
| C4 独立交付 | 在独立环境只导入合成数据，按说明运行连续任务及一次故障 | 可照说明启动并完成演示；合成数据能被检索，实例没有真实原文和登录态 | 隐藏依赖、数据域、默认过滤和配置 |

A／B／C 对应三轮的验收范围，每题可拆成必要的子案例；不为凑 16 题重复写已有测试。先复用已存在的测试与失败证据，再补缺口。源码中已有 A1、A2、A4、A5 等子机制的隔离证据，也不能把整组或真实任务标成通过。B5 等涉及真实模型决策的部分，用假模型无法验收。

所有题采用 `待执行／通过／失败／阻塞` 四种记录，并写明是函数、隔离集成、真实模型还是网页层；问题本身的研发状态另按下节维护。失败项附第一处偏离预期的证据，阻塞项附最小人工操作。测试前先指定环境：合成隔离库的维护诊断不能顺手改成对真实库执行恢复。

### 同类型问题怎样汇总，避免每个例子都补一条规则

先按表现归组，再用证据判断是否同一个原因。例如“搜索没结果”至少可能是：库里没有、数据还没处理、筛选不符、工具故障、模型没有正确调用。表面相同不等于同一个问题，不能统一靠放宽条件处理。

每组只维护一张问题卡，附全部已收集案例；下表是填写模板，数字必须实测后填写：

| 字段 | 填写内容 |
|---|---|
| 编号、来源与版本 | 请求／日志／受控合成；记录日期和代码版本，私有证据只存本机 |
| 用户影响与优先级 | 错误事实、漏掉岗位、无法完成，还是额外等待 |
| 样本与计数 | 检查多少、失败多少；原反例、正常对照及暂不用于调试的新请求 |
| 当前归因 | 已证实原因、待验证假设分别列；确定输入直接调用工具的结果 |
| 修复范围与验收 | 本轮只改哪个机制；什么可观测结果才算通过 |
| 状态与下一步 | 待复现／已定位／候选实现／隔离通过／待真实验收／已启用并观察 |

优先处理编造事实、违反硬条件、越权或错误写入；然后处理核心任务无法完成、数据不可用和错误状态；行为正确后再处理重复调用、等待与成本；新功能最后根据实际收益决定。优先级影响排队，不把尚未证实的假设写成已确认事故。新增问题的执行顺序仍只更新 PURPOSE。

同一组修复后，要重跑组内反例、正常对照和预留新请求。若只有某一句话变对、同类改写仍失败，就继续定位共因，不能靠不断添加例外词堆出“通过”。

## 4. 我怎样判断原因，而不是盲目改提示词

按请求经过的顺序检查，尽量找第一个出错的位置：

> 用户要求 → 本次条件 → 模型选工具与参数 → 工具执行 → 数据／索引 → 工具返回 → 回答与卡片 → 保存状态。

| 观察到的证据 | 优先检查 | 可能的修复位置 |
|---|---|---|
| 原始来源有记录，但没入库 | 来源访问、采集运行结果 | 采集适配或错误处理 |
| 原文入库，结构化字段缺失 | 抽取输入、截断、失败与待处理状态 | 抽取流程或数据处理 |
| 字段正确，检索查不到 | 对齐、切块、索引、筛选、检索降级 | 数据可用性或检索 |
| 工具可正确执行，模型传错城市 | 条件传递、工具说明、模型决策 | 编排或约束校验 |
| 工具说未知，回答说已下线 | 工具语义、提示和生成结果 | 契约或回答依据 |
| 回答按上海，卡片按北京 | 卡片计算条件和前后端传参 | 条件贯穿或展示 |
| 页面显示已保存，数据库没有记录 | 事务提交、异常、前端状态 | 保存流程 |

模型问题要用同一工具结果、不同表达或重复运行验证；接口问题用确定输入直接调用工具验证。可确定的状态含义、预算、硬条件和去重规则优先由程序保证。需要理解自然语言和组织解释的部分再交给模型。

一次失败可能有多个原因；先修一个机制，重新观察，再决定下一处。不能一次换模型、改提示、改检索后把变化都归功于其中一项。

### “接口不够工程化”具体查什么

不先重写全部接口。每轮沿失败路径核对下列契约，复用已有工具运行器、Pydantic 校验、数据库和 SDK；确认缺口才修改。

| 检查点 | 要明确的行为 | 验证例子 |
|---|---|---|
| 输入 | 必填、范围、默认值、当前条件来源 | 非法 ID、负数量在执行前被拒绝；本次城市不被旧偏好替换 |
| 输出 | 成功、空结果、未知、失败、部分完成各是什么意思 | HTTP 200 但返回局部失败不能记为全部完成 |
| 错误与重试 | 哪些能重试、间隔与次数、耗尽后怎么办 | 超时有限补跑；认证或验证码问题按来源规则停下 |
| 时间与预算 | 单次请求期限、总任务预算、分页及并发上限 | 单步不断重试也不能绕过任务总预算 |
| 重复与并发 | 唯一标识、事务、幂等范围和锁的覆盖面 | 双击保存、中途退出、两个 worker 同时执行 |
| 证据与可观测 | 版本、调用参数、结果状态、时间与错误能否关联 | 能区分“没岗位”和“没处理完”；私有原文不进入公开材料 |
| 兼容与使用方 | 改字段后谁还在用旧含义 | 工具说 unknown 时回答和卡片都不能写成已关闭 |

确定输入直接调用接口也失败，先查程序、数据或环境；接口可用但模型选错参数，才继续查条件传递、说明和模型决策。真实模型暂不可用时，假模型能验证控制流，真实选工具能力必须保留为未验收。

| 步骤 | 我负责做什么 | 交付给你什么 |
|---|---|---|
| 1. 核对现状 | 读当前路线、代码差异、历史证据；确认测试隔离和运行归属 | 已有能力、尚未验证和本轮范围 |
| 2. 收集与归类 | 整理同类失败，记录数量和总样本，不只挑最差例子 | 一张失败分组表，含正常对照 |

| 4. 提出设计 | 比较最小修复、组件复用和更复杂方案，说明代价 | 一页设计卡，推荐方案及原因 |
| 5. 实现一个机制 | 保留旧改动，尽量限制影响范围；必要时加兼容 | 可审阅代码差异及针对性测试 |
| 6. 分层验证 | 本地确定性检查、隔离集成、完整任务、预留请求 | 通过、失败、未执行及原因 |
| 7. 决定保留 | 正确性优先，再看时间、调用量和费用；无收益就撤回 | 前后对照和剩余问题 |

每轮聚焦一个问题，可包含必要的后端、前端和测试修改；“一个机制”不是强制只改一个文件。任务耗时依据复现和依赖确定，不预先承诺几天必完。

既有授权范围内的排查、案例准备和验证由我继续完成，不让你逐个批准命令。具体接口、数据结构或依赖选择如需确认，我会先给出可审阅的方案和推荐理由；你只需要理解行为和取舍。登录、账号开通和权限阻塞会列成待办，我跳过依赖它们的验证，继续做独立工作。

## 6. 贯穿示例：“采到了，却搜不到”怎么处理

这个问题已在隔离环境复现，工作区已有候选修复；整轮尚未验收、未部署。具体进展看 STATUS，实际候选契约看 [TECH 的知识补跑设计](TECH.md#知识补跑候选契约2026-10-21)。这里解释排查方法。

**先问**：原文是否真的入库？抽取是否成功？岗位是否对齐？检索块是否生成？关键词能否命中？向量是否完成？模型是否使用了正确筛选？

**再做最小实验**：在隔离库放一条合成岗位，受控地让知识处理中的一个步骤失败。保持没有新增原文，观察后续是否再次处理，并通过实际检索查验结果。不能仅看函数返回成功或日志“刷新完成”。

**设计候选**：复用已有数据库和待处理条件，比较“根据未完成数据发现待办”与“持久记录阶段状态”的复杂度，选择能覆盖复现的最小方案。先检查现有幂等性和失败返回含义，再决定是否需要新字段或迁移；不提前确定一套通用工作流引擎。

**必须考虑**：进程重启是否丢失待办；永久错误是否无休止重试；向量批次通过 `failed_groups` 返回的局部失败是否被遗漏；重试本身失败后如何可见。有限尝试后应保留可定位的未完成状态，不能无限承诺最终成功。

**怎样验收**：失败不计完成；没有新增也能按设计触发处理；重试次数和间隔有边界；相同条目不重复写入；关键词与向量可用状态分别验证；可选图谱失败不阻断不依赖它的查询。重试和进程重启只在隔离服务演练。

**怎样讲给你听**：“之前只有收到新包裹才整理仓库，上次没整理完、今天没新包裹就一直搁着。我们让未完成的整理任务也能被发现，但限制每次工作量和失败重试。”这个比喻用于理解，具体结论仍以代码与实验证据为准。

本轮还发现“货物登记了、整理任务没登记”的退出窗口，因此把抽取结果和待办放在同一数据库事务里：要么都保存，要么都不保存。它保证这两个状态一致，不保证每个步骤永远只执行一次，也没有自动找出历史上全部漏排队数据。

### 当前下一小步怎样提出，而不是笼统说“继续工程化”

**要回答的问题**：当维护任务显示 idle 或 ok 时，是否仍有历史数据没准备好？目前 `maintenance.status()` 只看最新任务，不能回答这个问题。没有任务是事实，“没有积压”则尚无依据。

我先给出诊断设计，再写反例和实现。诊断应把原文未抽取、结构化岗位未对齐、检索块缺失／过时、向量未就绪区分开，并说明检查范围、耗时及无法判断的部分。原文未抽取不由知识 worker 处理；已有完整数据可能因来源快照更新而需要重新对齐，因此不能只统计空外键或未生成向量数就宣称健康。如何判定这些状态，必须对照已有对齐与切块契约后确定，不在本文提前承诺字段或新接口。

恢复入口与只读诊断分开：恢复要明示排队对象及后续会执行什么，不能静默清空耗尽额度。验收先在隔离库准备“空库、历史漏排队、正常已完成、部分未完成、耗尽、来源快照更新”六类条件，检查实际数据与诊断是否一致，再验证排队行为。这个小步不包含启动采集、注册平台或修改真实数据。

**2026-10-21 实际进展：诊断／显式排队已有未提交实现，尚未通过验收。** 本次执行 `tests/test_knowledge_audit.py`，11 项中 9 项通过、2 项失败；使用隔离 `polaris_test`、合成数据和假向量服务。不能把命令已经存在写成“积压问题已解决”。这正好说明问题如何逐步提出：

| 从检查发现什么 | 关键代码证据 | 下一小步的设计与通过标准（未实现） |
|---|---|---|
| 岗位发布日期改变，正文不变；刷新后检索块日期仍旧 | `search/index.py` 的 `_sync_chunks` 只比较正文指纹，直接跳过该块 | 比较影响检索的元数据；同步日期而保留有效向量。原反例通过，再次同步无变化，不额外生成向量 |
| 向量为空，但已处理指纹恰好等于正文指纹；诊断指出不可用，处理器却不补 | `embed_pending` 的选取、写回与剩余统计仅检查指纹差异 | 三处统一采用真正的待处理条件，保留正文版本竞争保护。补出向量、实际检索命中，旧请求不能覆盖新结果 |

这两项属于数据处理契约，可用确定输入复现，无需先归为模型能力不足。处理后还要核对诊断与实际删除范围、直接刷新并发边界、实际检索和可用延迟；当前不保证诊断列出全部故障。这里只解释当前问题的工作方法，后续排期仍在 PURPOSE，实际状态见 STATUS。

## 7. 什么叫验证通过

### 不同检查能证明不同的事

| 检查层次 | 能证明 | 不能替代 |
|---|---|---|
| 函数／工具测试 | 给定输入，状态判断、参数校验等行为正确 | 真实模型会选对工具 |
| 隔离库集成 | 事务、待办、重试和保存行为符合预期 | 真实平台一直可访问 |
| 网页完整任务 | 输入、工具、回答、卡片和存储能够衔接 | 长期运行效果 |
| 预留请求与重复运行 | 改动不只适用于调过的几个例子 | 大规模统计结论 |
| 小范围真实自用 | 现实中哪些地方省事、哪些继续失败 | 因项目带来 offer 的因果证明 |

只加必要测试：有风险的行为、已复现的失败和关键契约值得测试；纯文字或低影响样式修改不为凑数编测试。

### 每个完整任务同时检查三件事

1. **结果**：要求是否满足，硬条件有无违反，事实能否回到来源，未知有没有被编成确定事实。
2. **过程**：工具和参数是否合理，是否重复绕圈，是否超预算，是否擅自放宽要求，是否在该停止时停止。
3. **保存状态**：实际落库内容是否正确，取消和中断是否如实记录，重复请求是否重复生效。

允许不同但合理的工具路径；不强制逐步模仿一条标准轨迹。硬条件、事实和权限错误单列，不能靠平均分掩盖。模型裁判只能辅助，失败或无法判断时保持待审。

### 前后对照怎么记

比较时尽可能固定数据快照、时钟、背景、模型及参数、预算和运行环境；无法固定的线上变化单列，不归因于改动。同一组模型任务建议先各运行三次观察波动；模型不可用或额度不足时记录缺口，不换成假结果。规模和重复次数可按成本调整，并公布实际次数。

| 记录项 | 记录方式 |
|---|---|
| 任务完成 | 通过数／总任务数；部分完成与失败分别列，附原因 |
| 严重错误 | 编造、违反硬条件、错误保存等逐项计数 |
| 无效调用 | 明确定义何为无效，保存具体轨迹供核查 |
| 用时 | 相同起止边界；保存各次值，小样本可报中位数及范围 |
| token／费用 | 记录各类调用；价格或计量不完整时只报告已知部分 |
| 数据延迟 | 从保存原文到具体检索方式实测可用的时间；未成功项也列出 |

不把模块通过数当任务成功率，不把小样本 P95 当稳定生产指标。曾经看过、调过的“测试集”只作回归，不再称未见请求。

### 每轮收尾的验收记录模板

记录追加到 DEVLOG；只有执行顺序变化才改 PURPOSE，当前事实更新到 STATUS。私有请求和完整轨迹留在本机，公开记录只放合成案例或适合公开的汇总。

```text
问题组／版本：
样本来源：真实自用／公开反馈／受控合成；各有多少。
环境：隔离库、数据快照、时钟、模型或假模型、预算。
结果前后：通过数／总数，严重错误逐项列，失败案例入口。
过程前后：实际工具及参数、执行次数、停止原因、用时和调用量。
状态前后：实际保存了什么；中断、重复和部分失败怎样记录。
新请求：是否在修改前预留，运行几次，何时转成回归材料。
未执行项：登录／额度／环境阻塞及影响，不能填为通过。
决定：保留／继续定位／撤回；原因及回退入口。
启用情况：仅候选／隔离通过／真实任务通过／已启用；分别附证据。
作者能讲清：原来为什么错、这次怎样保证、仍有哪些边界。
```

没有可比较的修改前证据，就只能报告当前行为；没有实际运行版本核对，就只能报告代码验证。先把缺口写出来，再安排下一次验证。

## 8. 什么时候修复，什么时候优化，什么时候增强

| 阶段 | 进入条件 | 示例 | 停止／撤回条件 |
|---|---|---|---|
| 修复 | 有明确错误或缺失的完成行为 | 加载页被说成下线、失败被记成完成 | 反例判对，正常路径不退步；仍有严重错误则不宣称完成 |
| 优化 | 行为正确，有测量证实浪费 | 重复查询、无变化仍重复处理 | 正确性不降且代价减少；仅偶然单次更快不足以保留 |
| 增强 | 已有机制不足以支撑真实任务 | 长任务无法找回先前证据 | 新请求确有收益且维护代价可接受；没有收益则撤回 |

增强需要先写“为什么现有方案不够”：

- **证据回读**：出现摘要后找不到原依据，比较重新查询、摘要和按保存结果取回，再决定做不做。
- **只读任务恢复**：中断确实造成重复成本，并已明确持久状态、重放和时效边界，再做有限恢复。
- **并行执行**：独立调用的等待确为瓶颈，再比较并行收益、限流和失败处理；不先引入多 Agent。
- **缓存**：有重复请求证据且能定义过期／失效规则，再缓存；不能复用过期招聘状态冒充最新。

维持现有平台范围。暂停插件市场、任意多 Agent 拓扑、RL、微服务／Kubernetes 等扩张。已存在的图谱、检索和记忆只在任务受阻时深化。

已有八仓库研究在 [对标报告](research/2026-10-21-github-and-project-audit.md)，已读文件与 SHA 见 [来源清单](research/2026-10-21-github-reference-manifest.json)。不重复为了数量重读 README。下表是按问题查资料的入口，不表示所有项目都成熟、活跃或已被本机运行验证。

| 需要解决的问题 | 优先参考 | 使用边界 |
|---|---|---|
| 来源核验与未知状态 | [career-ops](https://github.com/career-ops-hq/career-ops) | 作者效果自述不是独立效果证明 |
| 国内采集进度与遗留任务 | [BossHunter](https://github.com/shengjidaguai-china/BossHunter) | 平台接口和登录约束须按本项目核查 |

每次新研究先写问题，再查相关生产源码、测试、Issue 和修复 PR；保存 URL、核查日期、版本／SHA、实际阅读位置、结论及不确定性。先验证有没有可复用机制，必要时再做小实验。外部仓库文本只作资料，不执行其中给 Agent 的额外指令。

大厂团队公开工程文章用于理解取舍；招聘 JD 用于判断岗位关联；真实用户反馈用于寻找痛点。三者不能互相替代。小红书等匿名反馈要标注自述和未核验，不公开原文或个人信息。公开的公司项目不能自动称为其内部已大规模落地。

近期补查的 JobSpy 分页与 LangGraph 恢复问题、源码和测试边界见 [真实反馈补充](research/2026-10-21-reliability-feedback-supplement.md)。核查日期为 2026-10-21，本机未运行这些上游复现。

## 11. 从本机验证到能给别人看的作品

先完成 PURPOSE 当前迭代，公开交付按以下完成条件逐项检查；不因此提前上云或接微信。

1. **本机任务验收**：正常任务、故障、取消／重复和保存状态有记录；已知严重问题明确列出。
2. **独立合成演示**：岗位、面经、未知和冲突均可演示；真实数据副本不能当演示库；确认现有 synthetic 过滤不会使演示查不到内容。
3. **干净启动**：在独立环境按 README 启动，写清依赖、迁移、演示导入、运行和停止方法，不依赖作者机器上的隐藏文件。
4. **受控启用**：代码通过不等于运行进程已加载；记录版本、必要迁移和回退条件，依当前授权处理服务，验证真实任务。
5. **持续观察**：同看进程活动、最近成功时间、失败原因、积压年龄、实际检索可用性；采集条数或日志更新不能单独代表健康。
6. **反馈回流**：新问题回到第 3 节的问题卡，分组后进入下一轮，不能无限追加功能。

开始任何运行验证前确认对象是隔离服务还是自用服务。不得为测试停止／接管采集浏览器、重建冻结评测副本或改真实数据；不把历史“继续采集”的描述当成当前重启指令。缺登录、验证码或账号时如实报告阻塞。

### 持续采集和新数据怎样进入开发闭环

目标是及时发现停滞并能定位原因。开发助手在一次会话结束后不会自然变成持续运行的监控服务；当前不能承诺软件一直在线。以下是后续运行验收要检查的信号，不表示已有完整监控面板：

| 信号 | 怎样理解和处理 |
|---|---|
| 进程和计划任务 | 能否执行、运行的版本是什么；任务 Ready 不能证明正在采集 |
| 各来源最近成功时间与失败原因 | 按来源分别查，区分登录失效、限流、网络和代码错误；旧数据未新增也可能是正常结果 |
| 原文、抽取与索引积压 | 看未完成数量和等待时间；新增原文不能证明后处理完成 |
| 关键词／向量实际可用性 | 在隔离验证中实际查询目标条目，分别记录成功时间；避免只看刷新日志 |

自用采集与开发验证各有归属。先核查当前运行与授权，再安排启用和观察；不在修复时顺手重启采集或刷新真实数据。新出现的问题按来源和日期进入问题卡；对照实验继续固定快照，不能把数据自然变多造成的效果归功于代码。需要登录或人工处理时列明受影响来源、已完成的独立工作和恢复后的验证入口。

回退按改动性质设计：代码可恢复到已记录版本；数据库变更须考虑兼容和数据保留；已有真实写入不能靠撤回代码自动消除。不把“重置数据库”当通用回退方式，不覆盖其他未提交工作。

## 12. 你做什么，我做什么，怎样汇报

| 我负责 | 你负责 |
|---|---|
| 准备案例、查源码与真实反馈、定位问题、提出推荐方案 | 告诉我结果是否符合你实际找实习的需要 |
| 写代码、隔离测试、对照实验、记录失败和局限 | 在需要时完成本人账号登录／验证码或开通服务 |
| 解释技术取舍，说明证据与不确定性 | 理解每轮一个核心机制，逐步练习讲解和修改 |
| 维护文档、保留版本、整理可公开证明 | 决定产品取舍和是否执行对外动作 |

你不需要先准备一大批资料。你随时想到的真实问题很有价值；没有新问题时，我先用已有记录和标注清楚的合成案例继续。真正需要你处理的事情会单列，包含影响范围和我已完成的部分。

工作中在发现根因、设计变化、验证结果或阻塞时及时汇报。长时间工具工作也会给进度，但不能把计划写成完成。日常汇报固定说清：

```text
本轮问题：一句普通话。
已核实：实际证据和当前根因。
本轮设计：只改哪个机制，为什么。
结果：修改前后各多少案例通过；哪些失败／未执行。
代价与局限：用时、调用量、维护影响及无法证明的部分。
你需要处理：没有就明确说没有；有则写最小必要动作。
下一步：哪一项验证或问题，不提前展开多条研发线。
```

每轮收尾请你尝试用自己的话解释三件事：“以前为什么错”“这次靠什么保证”“还有什么保证不了”。答不上来时我补讲并给一个小调试练习，不用一次记住整个系统。

## 13. 如何成为能经得住追问的求职作品

对 HR，先展示谁在用、解决什么问题、作者负责什么，以及可打开的演示和仓库。对技术面试官，准备两至三个完整案例，能沿证据追问到代码。

候选案例包括：来源核验中未知与关闭的区分、数据已采集但未可检索、临时条件和长期偏好的边界。前两者已有工作区候选与隔离证据，整体验收及后者核查继续按路线推进；候选不能写成线上成果。

每个案例保留“需求 → 反例 → 根因 → 替代方案 → 实现 → 前后对照 → 未解决范围”。没有线上事故就称受控反例，没有真实用户就称作者自用，没有实测提升就不写提升。

最低作品材料：两分钟合成演示（含一次失败处理）、清晰 README、干净启动说明、真实测试记录、两至三个工程案例和明确的个人贡献。诚实区分框架能力、自己设计的机制和 AI 辅助；作者要能解释、修改和调试关键代码。

个人贡献按三类列清：框架提供执行／持久化基础；作者负责需求取舍、领域状态、条件与证据契约、故障实验和验收；AI 协助代码、资料和测试。只认领自己实际参与并能解释的部分。每个案例练一次“改参数触发失败 → 找到记录 → 解释设计 → 修改并复测”，比背技术名词更能检查理解。

效果先看有效岗位发现、误判／漏检、任务完成、人工核查时间和调用成本。计量方法与样本一同公开；少量 offer 或求职结果不能归因于 Agent。没有实际用户数据前，不编“服务多少用户”“效率提升多少”。

## 14. 下一次开工的第一句话

> 按 PURPOSE 当前迭代卡继续数据可用性。先读 STATUS 与 TECH，保留并核对已有候选和前端修改。知识补跑及事务排队已有隔离证据，不重复实现；先检查历史未排队积压如何显式发现、直接刷新入口的并发边界，再完成实际可用延迟和真实任务验收。不要重启采集，不重建冻结副本，不从零再做一轮竞品普查。
