# 宗旨

这份文件写的是为什么做这个项目。其他文档讲怎么做；取舍拿不准的时候回到这里。

## 最终目的

找到 LLM 和 Agent 方向的实习。北极星是达到这个目的的手段，它有两层作用：

1. **它是证明材料。** 简历上一条能被 HR 逐项点开核实的经历：有在线演示、有公开仓库、有文档、有视频、有指标。
2. **它是工具。** 做出来以后，作者自己用它找实习。

黑客松提供的是截止日期和一个公开的出处，不是目的。拿不拿奖不重要。

## 为什么是这个题目

作者在北方读本科，方向是 LLM、RAG、Agent。实习机会和求职信息集中在南方和几个科技中心城市，不在那里的学生看到的岗位少、知道得晚、认识的人少。北极星要补的就是这个差距。这也是比赛"潜在影响"一项的真实依据：作者自己就是目标用户。

## 作者对项目的要求

- 能体现技术含量，对得上真实 Agent 开发岗位的要求。
- 是多种技术配合的完整系统：记忆、检索、图谱、工具、评测一起工作，不是单点技术的演示。
- 做深工具调用与任务编排；用真实任务和前后对照证明改进，能说清好在哪、差在哪。
- 从需求到上线每个阶段都可追溯：需求从哪来、产品怎么取舍、怎么开发、怎么评测、怎么上线、用了之后有什么反馈，都留下文字和提交记录。
- 实用、方便，作者自己真的会每天用。
- 技术侧重点及后续路线统一见下面“现在的目标”（10-21 更新）。
- 技术栈要有依据：按真实 LLM 和 Agent 岗位的要求选型，调研、比较、小实验验证后再定，不凭印象。（2026-10-11 加）
- 先大量采集、建自己的数据集：近半年（2026-04 起）的大厂岗位、面经、内推和讨论，格式固定、可追溯。来源含小红书、Boss、脉脉、牛客、大厂官网。脉脉也自动采，但只采内容、不采人。每个平台只用作者本人一个账号，慢速、只读，不伪装、不绕过平台的限制。见 `DATASET.md`。（2026-10-11 加）

## 现在的目标（2026-10-21 更新）

**最终目的不变**：找到 LLM / Agent 方向的实习。北极星既是证明材料，也是作者自己每天用的工具。

**产品定位**：面向中国 LLM / Agent 实习求职者的证据型求职工作台。用一条连续任务验收：按本次条件找岗位 → 核验时效和来源 → 解释符合、不符和未知 → 按所选岗位生成有依据的面试准备 → 记录用户确认的跟进。区分日常实习、校招与社招，关注学历、论文、到岗要求及面经归属。该定位在现有求职 Agent 范围内收敛；具体接口设计和收益仍需验证。

**技术侧重点：真实求职任务中的可靠工具调用与任务编排。** 条件不跑偏、工具选得对、失败能处理、结果能追溯、过程能保存。
检索、多来源冲突处理、长期记忆作为已有能力维护；只有证据表明它们阻碍当前任务时才修复。评测服务于产品改进，不作为独立研发主线。
为什么选它：作者瞄准的岗位（北京、Agent、实习、非纯算法，72 个）里 55% 提到编排相关能力，检索和记忆各 30%；902 道一手面经题里相关的分别是 137、102、53 道；
10-12 的几轮实测里，能稳定量出来的改进都来自这一层。详见 `HIRING.md`、`design/DEPTH.md` 第四轮。

10-21 补充调研已保存：[生产方向与岗位/面经样本](research/2026-10-21-production-direction.md)、[GitHub 对标与代码审计](research/2026-10-21-github-and-project-audit.md)。历史统计与新样本口径不同，不直接拼接。重点做条件和证据贯穿的可靠执行，以及可审查、可中断并按边界恢复的过程；上下文工程以实际失败为依据，评测贯穿修改。沿用当前技术栈，不扩成通用 Agent 平台。比赛时间与硬要求查 HACKATHON，提交前重新核实，不把文档历史核查当最新报名状态。

**工作方式：老师带着做，不一口气做完。**（作者 10-12 提出：自己还不懂这个方向，一口气做完就不知道哪里该调，面试也讲不清）

具体的提问、定位、修复、增强、验证、交付和协作方式见 [整体开发手册](DEVELOPMENT.md)。手册解释怎么执行，本文件仍是目标和后续路线的唯一入口。

- 每一轮：开发助手把真实运行记录摊开 → 作者按自己找实习的真实需要逐条判断（作者是这个领域的专家）→ 归类、数清每类多少 → 作者挑一类 → 只改一处 → 量改动前后（包括没见过的题）→ 作者决定留下或撤回。
- 测试和讲解以做过生产的人的经验为依据（课程、工程博客、事故复盘），题目优先用作者真实想问的，不只用开发助手自己编的。
- 开发过程只记在一个文件 `DEVLOG.md` 里，持续更新：看了什么、发现什么、改了什么、结果、作者学到什么。这就是面试时的讲法。
- 开发助手每一步要讲清：在做什么、为什么、面试官和 HR 在这一步看什么。

**作者要能讲清的四件事**（面试官判断"有没有深度"的依据）：

1. 它在哪几类问题上会错，各占多少；
2. 每个改动针对哪一类，在没见过的题上好了多少，多花了多少时间和钱；
3. 哪些做法试过没用、为什么撤回；
4. 怎么控制它：能做什么、不能做什么（权限）；哪些要人批准；查多少次、花多少钱就停（预算）；每一步都留记录能回看（追踪）；出错了怎么停下、怎么恢复。

### 后续路线（唯一维护入口；10-21 调研后更新）

1. **来源核验可信性（候选已实现）。** 已处理加载页及“该职位已更新”误判下线：区分开放、关闭与无法核验，网络/认证/未加载不映射成确定关闭。假来源和隔离回归通过；未用真实平台验收，未部署。详见 HANDOFF 第一轮。
2. **从采集到可检索的数据可用性（进行中）。** 官网每日批次只把成功运行算完成，失败来源冷却后重试；普通采集轮次即使没有新原文也会限量补抽当前来源旧积压，失败抽取仍留待下轮重试。知识补跑已有持久阶段、有限重试和 daemon 独立触发候选；抽取结果／官网成功快照和待办同事务提交。隔离验证覆盖无新增、真实子进程退出、部分向量失败、并发和耗尽；没有真实平台／模型验收或部署。下一步收拢历史未排队积压的发现与人工出口、直接刷新入口的并发边界，再测真实处理链的实际可检索延迟和完整任务；保持已有平台范围和配额。具体候选契约及限制见 TECH，不能因此宣称整条采集链已可靠。
3. **本次条件与结果解释一致。** 核查当前查询、长期画像、工具和卡片采用的条件；未知不当不符，硬冲突不能由高分抵消。结合已有卡片改动完成端到端验证。空结果继续区分覆盖不足、漏召回、条件不符、工具故障及模型决策错误；有限补查且不放宽硬条件，不把一次空搜索推为全平台无岗。
4. **真实任务对照与独立交付。** 固定数据/时间/背景/模型/预算，一轮只加一个机制，修改前预留新需求并重复运行；同时核对任务结果、过程和保存状态。打通纯合成独立演示和干净环境启动，再完成比赛模型与提交材料。小范围体验、保留回滚点，用户反馈转回归。

以上是先后顺序，不是同时启动四条研发线。每轮沿用“定位失败 → 作者判断 → 一个机制 → 同条件对照和预留需求 → 决定保留/撤回”的工作方式。旧空结果专项已有候选，历史数据不重复当新成果。证据回读、只读任务自动恢复及并行研究，在相应失败得到证明后才作为后续实验；当前持久化不等于无缝恢复。

#### 接下来三轮的执行卡（计划，未验收）

| 轮次 | 具体问题 | 实现边界 | 完成标准 |
|---|---|---|---|
| 第一轮：知识处理失败后继续推进 | 已采集或抽取的数据，因知识层失败且没有新增而停留在不可用状态 | 先用隔离库／假故障复现，比较已有待办查询与阶段状态记录，选择最小方案；明确重试间隔、次数、每轮处理上限和人工处理出口，不扩平台或建通用调度平台 | 无新增时失败项仍能按设计重试；重启隔离服务不丢必要待办；局部失败不计完成；重复处理无重复写入；关键词和向量实际可用分别核验；重试耗尽可定位且不无限循环；记录原文入库到可检索延迟及未成功项。具体限制值在设计卡中说明并测试边界 |
| 第二轮：本次条件贯穿结果 | 临时条件、长期画像和卡片解释可能不一致；空结果原因需要真实区分 | 先核对既有前端改动并复现，再修已确认的条件传递／解释缺口；维护现有记忆，不重写整套记忆系统 | 北京长期偏好／本次上海、到岗天数未知、学历硬冲突及真实零结果均有完整任务验收；工具、回答、卡片一致；长期偏好不被误改；未知不冒充符合或不符；补查有限且不擅自放宽硬条件 |
| 第三轮：完整任务对照和独立交付 | 模块测试与他人可使用的作品之间仍有缺口 | 初始 12–20 个覆盖主要失败类型的任务，保留新请求并重复运行；建立纯合成演示和干净启动；先不增加平台或框架 | 固定比较条件并保留结果／过程／状态证据；失败和未执行分开报告；演示可完成核心任务并展示一次故障处理；独立环境按说明能启动；确认真实原文／个人信息／登录态未进入演示；README、两分钟演示和工程案例均与实测一致 |

第一轮当前小步：先修已复现的旧对齐／切块覆盖新结果、题目与块部分提交及调用方旧缓存；随后收拢清理与历史恢复的执行保护，最后测整链可检索延迟。竞争必须保持新待办和既有失败预算；一次同步失败不能留下半套派生结果。具体设计与反例见 DEVELOPMENT 第 6 节，实际红绿状态见 STATUS。不能只因同一批数据重复执行无变化，就认为并发执行也安全。

一轮内部可按一个机制拆成多个可运行小步。已有候选先复核，不重复实现。新增字段、接口或依赖先给可审阅设计；真实平台／模型依赖缺失时保留待验收状态，不用模块通过替代。小样本任务用于暴露错误，不支持预先承诺成功率或统计显著的性能优势。

### 验证标准与停止扩张的方向

- 同时检查**任务结果、执行过程和保存状态**：需求是否满足、硬条件是否遵守、工具及参数是否合理、事实能否回到原始来源、记录是否实际落库。允许合理的不同路径、等价查询和复用前轮证据。
- 在正确性不退步的前提下比较无效调用、耗时和 token；费用只在计量覆盖完整且价格有据时报告。越界请求被拒绝是约束生效，也仍是模型决策失败，不能只统计执行成功率。
- 保存原问题、完整工具输入输出、错误分类、预期行为、修改版本和复测结果。规则检查可核实的事实，人工核对关键样本，模型裁判只辅助；裁判失败保持待审，不靠平均分抵消事实错误。
- 已看过的留出/测试题转为回归材料，不能反复调试后仍称未见测试。历史模块分数不代表当前端到端质量，自建题集不冒充官方 benchmark 成绩。
- 取消“所有模块扩一套新 benchmark”“每日所有回答都交模型评分”“先完善通用评分器再修产品”的路线。保留必要回归和原始失败证据，不为凑指标添加工具、多 agent 或记忆功能。

**本轮后续的验收目标**：在上述空结果与故障场景中，能保持条件、合理补查或停止、如实解释并保留证据；正常有结果的任务不因限制过严而漏答。具体效果以对照结果报告，不能预先宣称提升或生产可用。

### 生产实践依据（10-13 联网核实）

- [Anthropic 工具工程](https://www.anthropic.com/engineering/writing-tools-for-agents)：从真实轨迹定位工具说明、冗余调用和参数问题，允许多条有效路径。
- [Google ADK 评测标准](https://adk.dev/evaluate/criteria/)：分别评价工具使用、多轮过程和最终回答。
- [Anthropic 生产架构复盘](https://www.anthropic.com/engineering/managed-agents)：会话记录与执行解耦；模型变化后重新检查执行层补丁是否仍必要。
- [LangChain 反馈闭环](https://www.langchain.com/resources/ai-observability)：真实失败 → 修正记录 → 可重复案例 → 修改与发布后验证。

这些资料支持工程路线；不证明本项目已达到生产质量，也不是大厂招聘的统一标准。

## 行动准则：一份求职教练的做法

来源是一段约三分钟的直播，一位求职教练给一名学生的建议，外加一张现场笔记的截图。作者认为它的中心思想是对的，要求这个项目向它靠。下面是转述，不是原文。

**中心思想：offer 靠三样东西相乘拿到，能被核实的证据、主动触达的数量、每一次都跟进。** 作品要别人点开就能看，人要自己去找，投出去的每一份都要追。

1. **作品能直接访问。** 部署上线，配好 HTTPS，给面试官一个现成的账号，点开就能用。笔记里列的是：作品集网站、给项目画架构图、把技术栈梳理一遍、录演示视频、用云厂商的学生机部署。
2. **项目上 GitHub，重点是 README。** 代码本身不是最重要的。README 要写清怎么运行、有可视化的架构图、有哪些接口、怎么最快跑起来、贡献者是谁、项目产生了什么影响。
3. **外企和国内大厂同时投。** LinkedIn 上每天投二三十份，同时走各家官网。
4. **用脉脉找校友。** 每天约五到十个电话或咖啡聊天，请他们内推。坚持三周能约到两百多个，一定有人愿意给机会。
5. **Boss 上投递时主动讲条件。** 说明自己可以提前来实习、希望拿转正。
6. **没回音就直接找人。** 找到公司的 HR，想办法查到企业邮箱，发邮件自荐。
7. **数量做到极致。** 五十封不够，每天二十封，做到一千封。第三方平台全部投满。
8. **每次投完都跟进。** 问对方为什么没回复、有什么建议，每条消息都附上自己的作品链接。
9. **作品集做成 PDF。** 做多个版本，哪个对方容易打开就发哪个。

### 两处不照搬

- **买 star 不做。** GitHub 政策禁止刷星，后果是封号或删内容；买来的星来自空号，点开列表就能看出来，和"留下能核实的证据"正好相反。星数靠真实渠道攒。
- **现成账号不挂在自用的实例上。** 公开演示单独一个实例，只放合成数据，给只读演示账号。作者的真实聊天、登录态和个人信息在另一个实例里。

## 这对开发意味着什么

- 每个模块做完都要留下一样能给别人看的东西：一个能运行的入口、一张指标表、一段提交记录。
- 上面九条做法怎么对应到功能，见 `PLAN.md` 第 10 节。提交时要逐项核对的证据清单也在那里。
- 取舍时问两个问题：这样做，HR 点开能核实吗？这样做，作者会不会少漏一个岗位、少漏一次跟进？两个都不沾边的功能，往后排。
