# 北极星：总体框架和开发顺序

2026-10-10 初稿；2026-10-11 根据技术调研重订（依据见 `INTRO.md`、`STACK.md` 和 `research/`）。讲"怎么做"的文档和本文件冲突时以本文件为准；"为什么做"以 `PURPOSE.md` 为准。

## 1. 方向

这个项目的最终目的是帮作者找到 LLM 和 Agent 方向的实习。它既是简历上一条能被 HR 逐项核实的经历（在线演示、公开仓库、文档、视频、指标），也是作者自己每天用的工具。

北极星是一个常驻云端的求职个人 agent，对标 Meta Muse 和 OpenAI Dots，只做求职这一件事。项目介绍和核心技术点见 `INTRO.md`。

开发上的四条主线：

1. **工具调用是主线。** 字节的 Agent 实习岗位里 74% 提到它。
2. **评测和 harness 贯穿全程。** 每个环节都有标注集和指标，有录制回放和故障注入，用 pass^k 衡量稳定性。
3. **重点打磨存储检索和冲突处理。** 包括多来源信息的矛盾裁决、记忆的新旧冲突、中文混合检索。
4. **固定流程写成代码工具，agent 只做需要判断的环节；多 agent 采用"一个写、多个读"。**

## 3. 架构

```
        你 ── 网页（Next.js 加 Vercel AI SDK，后期加微信）
                         │ 流式接口
                         ▼
 Polaris Core（FastAPI）
 ├ 主 agent（LangGraph，LangChain create_agent 加中间件）：每日计划、调用工具、写简报和草稿
 │    ├ 侦察子 agent ×N（Send 并行，只读）
 │    ├ 审查（干净上下文）      ├ 守门（规则加不能调工具的模型，人工审批中间件）
 │    └ 工程师（Docker 沙箱里写代码；只读账号查库）
 ├ 工具层（按功能分组、加前缀命名；同时以 MCP 开放）
 │    jobs_*：采集、抽取、对齐裁决、入库    search_*：中文关键词加向量加重排
 │    memory_*：双时间线事实读写            draft_*：简报和消息草稿    sql_*：只读查库
 ├ 定时：APScheduler 每天 06:00
 └ 评测：Polaris-Bench（录制回放、故障注入、pass^k）；自有追踪表；开发期加 LangSmith
                         │
 Postgres 17 加 pgvector：业务表、向量、中文全文索引、图谱边、记忆、LangGraph 检查点、调用追踪
                         │
 模型：开发期是第三方 OpenAI 兼容服务加阿里云；正式用 Token Factory 的 Nemotron 加 Qwen 向量和重排

 本机采集器（B 档）── HTTPS 推送 ──► /api/ingest/raw-items
```

## 4. 数据源分档

| 档 | 来源 | 在哪跑 | 进公开演示 |
|---|---|---|---|
| A | 国内大厂招聘官网（先做字节、小红书，两家今天都实测能访问）；外企招聘系统的公开接口（Greenhouse、Lever、Ashby）；Tavily；用户粘贴或转发的内容；GitHub；合成数据 | 云端 | 是 |
| B | 小红书社区（xiaohongshu-mcp）；Boss直聘（boss-cli）；牛客的实习和面经；LinkedIn 的公开岗位页（JobSpy，不登录） | 用户自己的电脑 | 否 |
| C | 脉脉和 LinkedIn 上的人：校友、内推人、HR | 不采集 | 否 |

用户已确认 B 档要做，小红书和 Boss 是必做项。

**为什么 B 档不进公开演示。** 比赛规则原文要求第三方数据"按其条款和许可使用"；这几个平台都没有查到面向个人的官方读取接口，现有工具全是浏览器自动化或逆向接口。功能照做，自己照用，但公开演示、视频和提交材料里只出现 A 档和合成数据。

**B 档的规矩。** 只读，不自动发评论、不自动打招呼；每个源每天最多跑两三次，单次只取前几页；采到的原文只留在用户自己的库里，不进仓库。

**C 档怎么做。** agent 负责出名单要求、起草话术、记录每次约聊、到期提醒跟进；用户自己在脉脉和 LinkedIn 上找人、发消息，把对方的主页或回复粘回来。

所有采集器实现同一个接口：输入查询条件，输出"原始条目"（来源、链接、抓取时间、原文、内容哈希）。A 档和 B 档只是运行位置不同，后面的抽取、对齐、匹配完全共用。

### 4.1 怎么采：按方向找岗位，不按公司名单

| 步骤 | 做法 |
|---|---|
| 1. 扩展查询词 | 模型把方向展开成一批查询词：同义说法、相邻方向、中英文写法，以及"能力 × 垂直领域"的组合 |
| 2. 搜索型来源直接搜 | Boss、小红书、牛客、LinkedIn、Tavily 本身就是按关键词搜全平台 |
| 3. 官网型来源整批拉 | 官网一个站就是一家公司，把这家的实习岗位整批拉下来，不按标题过滤。字节官网的列表接口带签名，用浏览器加载列表页、读取接口返回（2026-10-11 实测） |
| 4. 按 JD 内容匹配 | 匹配看 JD 正文的语义，不看标题里有没有关键词 |
| 5. 从结果里继续发现 | JD 里出现的新说法补进查询词；反复出现的公司补官网适配器；链接指向某个招聘系统时，自动登记这个入口 |
| 6. 归类输出 | 先按方向归类，方向下面列公司，公司下面列岗位。大厂单列一栏 |

这套发现机制单独评测：人工找 20 个标题不含方向关键词、但内容相关的岗位，看系统能召回几个。

### 4.2 每条岗位记哪些时间

采集从 2026-10-10 起算，下面的时间都是岗位自己的。

| 字段 | 含义 |
|---|---|
| 发布时间 | 来源页面上写的发布或更新日期，很多站不给 |
| 首次发现时间 | 北极星第一次采到这条岗位的时间 |
| 最近一次看到 | 最近一次采集时它还在不在，用来判断是否已下架 |
| 投递截止日 | 岗位写明的截止时间 |
| 最早到岗时间 | 岗位要求什么时候能入职 |
| 实习时长 | 岗位要求实习几个月 |
| 每周天数 | 岗位要求每周到岗几天 |

"近 7 天新增"按首次发现时间算。第一次采集得到的是存量，标成基线，不算新增。

## 5. 云主机

| 方案 | 结论 |
|---|---|
| AutoDL | 不能用：没有独立公网 IP，个人账号给不出公开演示链接 |
| 阿里云香港轻量（通用型） | **选它。** 免备案；对大陆访问友好。2 核 4 GB 每月 112 元，4 核 8 GB 每月 224 元 |
| 阿里云大陆机房 | 用域名对外提供网站要备案，来不及 |
| Nebius 主机 | 境外线路，没有优势；规则不要求主机在 Nebius |

- 先买 2 核 4 GB；要试 OpenShell 再升 4 核 8 GB。
- 买一个便宜域名，用 Caddy 自动签 HTTPS 证书。简历上的链接用域名。
- 从 10-27 开到 12-15，按月买两个月。

## 6. 微信

放在提交之后做，限时半天。两条路：Hermes 自带的微信渠道（底层是腾讯 iLink Bot），或直接接 iLink。

- bot 不能凭空主动发消息，每条消息都要带用户最近一条来信里的令牌。所以简报先尝试推送，推不出去就存着，等用户发一句话再回。
- 备用推送用 WxPusher 或邮件，只发一句"简报好了"加链接。

## 7. 模型分工

| 用途 | 正式（Token Factory） | 开发期 |
|---|---|---|
| 批量抽取、分类、侦察子 agent | `nvidia/Nemotron-3_5-Lightning` | `deepseek-v4.1-flash` |
| 主 agent、裁决、审查 | `nvidia/nemotron-3-super-120b-a12b`，推理打开 | 同上 |
| 每日简报、难例裁决、评审模型 | `nvidia/Nemotron-3-Ultra-550b-a55b` | 同上 |
| 向量 | `Qwen/Qwen3-Embedding-8B`（1024 维） | 阿里云 `text-embedding-v4`（1024 维） |
| 重排 | `Qwen/Qwen3-Reranker-8B` | 阿里云 `qwen3.7-text-rerank` |

预算：Token Factory 额度共 $50，要撑到 12-15。多 agent 的 token 用量约是普通对话的 15 倍 [A1]，所以子 agent 只用在并行采集上；评测反复跑时缓存模型输出。
