# 北极星：总体框架和开发顺序

2026-10-10 初稿；2026-10-11 根据技术调研和用户的要求重订（依据见 `INTRO.md`、`STACK.md` 和 `research/`）。讲"怎么做"的文档和本文件冲突时以本文件为准；"为什么做"以 `PURPOSE.md` 为准。

## 1. 方向

这个项目的最终目的是帮作者找到 LLM 和 Agent 方向的实习。它既是简历上一条能被 HR 逐项核实的经历（在线演示、公开仓库、文档、视频、指标），也是作者自己每天用的工具。

北极星是一个常驻云端的求职个人 agent，对标 Meta Muse 和 OpenAI Dots，只做求职这一件事。核心链路是：**采集 → 知识图谱 → 记忆 → 推荐**。项目介绍和核心技术点见 `INTRO.md`。

开发上的主线：

1. **信息采集以小红书为核心**，横向和纵向都深挖；Boss直聘大量搜索和筛选；大厂招聘官网整批拉取。**只看风向标大厂。**
2. **工具调用贯穿全程**：采集、抽取、建图谱、读写记忆、检索、起草都是工具调用。
3. **重点打磨存储检索和冲突处理**：知识图谱、多来源的矛盾裁决、记忆的新旧冲突和压缩、中文混合检索。
4. **评测和 harness 贯穿全程**：每个环节都有标准答案集和指标，有录制回放和故障注入，用 pass^k 衡量稳定性。
5. **固定流程写成代码工具，agent 只做需要判断的环节**；多 agent 采用"一个写、多个读"。

## 3. 架构

```
        你 ── 网页（Next.js 加 Vercel AI SDK，后期加微信）
                         │ 流式接口
                         ▼
 Polaris Core（FastAPI）
 ├ 主 agent（LangGraph，LangChain create_agent 加中间件）：每日计划、调用工具、推荐、写简报和草稿
 │    ├ 侦察子 agent ×N（Send 并行，只读）：小红书、Boss、各大厂官网
 │    ├ 审查（干净上下文）      ├ 守门（规则加不能调工具的模型，人工审批中间件）
 │    └ 工程师（Docker 沙箱里写代码；只读账号查库）
 ├ 工具层（按功能分组、加前缀命名；同时以 MCP 开放）
 │    xhs_* / boss_* / site_*：采集（只读）   jobs_*：抽取、对齐裁决、入库
 │    graph_*：知识图谱读写   search_*：混合检索、重排   memory_*：记忆读写和压缩
 │    draft_*：简报和消息草稿   sql_*：只读查库
 ├ 定时：APScheduler 每天 06:00
 └ 评测：Polaris-Bench（标准答案集、录制回放、故障注入、pass^k）；自有追踪表；开发期加 LangSmith
                         │
 Postgres 17 加 pgvector：岗位、笔记、知识图谱、记忆、向量、中文全文索引、检查点、调用追踪
                         │
 模型：开发期是第三方 OpenAI 兼容服务（deepseek-v4.1-flash）加阿里云（向量、重排）

 你的电脑：xiaohongshu-mcp（小红书，扫码登录）、boss-cli（Boss，浏览器登录）
```

| A | **牛客**：面经、讨论（公开页面，robots.txt 允许） | 站点地图 + 公司面经列表，礼貌速度 | 本机，上云后在云端 | 否（原文只在本机，汇总可公开） |
| C | 脉脉和 LinkedIn 上的人：校友、内推人、HR | 不采集。agent 出名单要求、起草话术、记录约聊、提醒跟进 | — | 否 |

**为什么小红书和 Boss 不进公开演示。** 比赛规则要求第三方数据"按其条款和许可使用"；这两个平台都没有面向个人的官方读取接口，现有工具都是浏览器自动化或逆向接口。功能照做，自己照用，但公开演示、视频和提交材料里只出现大厂官网数据和合成数据。

**小红书和 Boss 的规矩：规模大，但节奏慢。**
- 查询词多、覆盖广，但请求分散在全天，随机间隔，只抓新的，已采过的不重复抓。
- 只读：不评论、不点赞、不发布、不打招呼。
- 只用你本人的一个账号；登录态过期时提醒你重新登录。
- 原文只留在你自己的库里，不进仓库。
- 风险：用的是你自己的账号，抓得太密可能被平台限制。所以每个工具都限速，被限流时自动退避，并把限流次数记进指标。

所有采集器实现同一个接口：输入查询条件，输出"原始条目"（来源、链接、抓取时间、原文、内容哈希）。后面的抽取、建图谱、对齐、推荐完全共用。

### 4.1 怎么采：按方向找，只留大厂

| 步骤 | 做法 |
|---|---|
| 1. 扩展查询词 | 模型把方向展开成一批查询词：同义说法、相邻方向、中英文写法，再和大厂名单、岗位类型组合（如"字节 Agent 实习""腾讯 大模型 面经"） |
| 2. 小红书横向 | 用这些查询词搜笔记，按发布时间、排序方式筛选，按笔记编号去重 |
| 3. 小红书纵向 | 提到大厂、实习、内推、面经的笔记才展开：读评论和楼中楼，看作者主页和他的其他笔记 |
| 4. Boss | 同一批查询词，多城市、多页搜索，按公司规模、融资阶段筛选，再按大厂名单过滤 |
| 5. 官网整批拉 | 一个官网就是一家公司，把它的实习岗位整批拉下来，不按标题过滤 |
| 6. 按内容匹配 | 匹配看 JD 正文和图谱里的相关笔记，不看标题里有没有关键词，冷门岗位也能找到 |
| 7. 从结果里继续发现 | 笔记和 JD 里出现的新说法补进查询词；新出现的团队和部门补进图谱 |
| 8. 归类输出 | 先按方向，方向下面按公司，公司下面列岗位和相关笔记 |

### 4.2 每条岗位记哪些时间

采集从 2026-10-10 起算，下面的时间都是岗位自己的。

| 字段 | 含义 |
|---|---|
| 发布时间 | 来源页面上写的发布或更新日期 |
| 首次发现时间 | 北极星第一次采到这条岗位的时间 |
| 最近一次看到 | 最近一次采集时它还在不在，用来判断是否已下架 |
| 投递截止日 | 岗位写明的截止时间 |
| 最早到岗时间 | 岗位要求什么时候能入职 |
| 实习时长 | 岗位要求实习几个月 |
| 每周天数 | 岗位要求每周到岗几天 |

"近 7 天新增"按首次发现时间算。第一次采集得到的是存量，标成基线，不算新增。

## 5. 云主机

| 方案 | 结论 |
|---|---|
| AutoDL | 不能用：没有独立公网 IP，个人账号给不出公开演示链接 |
| 阿里云香港轻量（通用型） | **选它。** 免备案；对大陆访问友好。2 核 4 GB 每月 112 元 |
| 阿里云大陆机房 | 用域名对外提供网站要备案，来不及 |

- 买一个便宜域名，用 Caddy 自动签 HTTPS 证书。
- 小红书和 Boss 要用你本人的账号，境外机房的 IP 加个人账号登录风险最高，所以上云后这两个采集器仍在你电脑上跑，结果推到云端。

## 6. 微信

放在提交之后做，限时半天。两条路：Hermes 自带的微信渠道（底层是腾讯 iLink Bot），或者直接接 iLink。bot 不能凭空主动发消息，简报先尝试推送，推不出去就存着，等你发一句话再回。

## 7. 模型分工

| 用途 | 开发期（本机） | 提交时 |
|---|---|---|
| 批量抽取、侦察子 agent | 第三方服务上的 `deepseek-v4.1-flash` | Nemotron Lightning |
| 主 agent、裁决、审查 | 同上 | Nemotron Super |
| 每日简报、难例裁决、评审模型 | 同上 | Nemotron Ultra |
| 向量 | 阿里云 `text-embedding-v4`（1024 维） | Qwen3-Embedding-8B |
| 重排 | 阿里云 `qwen3.7-text-rerank` | Qwen3-Reranker-8B |

多 agent 的 token 用量约是普通对话的 15 倍 [A1]，所以子 agent 只用在并行采集上；评测反复跑时缓存模型输出。
