核查日期：2026-10-21。对象：本地 HEAD `d816fbf1b23517ab6b6b6e9af8d2766b5c76a233` 与当前工作区。保留原有三个前端未提交修改。本轮只做调研、代码核对、隔离测试与合成探针，没有修改产品代码、配置或采集进程。

## 结论

北极星正在沿“可靠工具调用与任务编排”发展，已有实质实现，不需要重建整个项目。但当前证据只能支持“有工程化基础、真实任务尚待整体验收的个人产品”，不能称为已经生产可用。

上一轮提出的 Harness 方向需要进一步限定：在真实求职任务中实现可验证的执行机制，而不是把项目改造成通用 Agent 基础设施平台。产品定位建议收紧为：**面向中国 LLM / Agent 实习求职者的证据型求职工作台，帮助用户判断今天哪些岗位值得投入、依据是什么、还缺什么核实，并把岗位要求连接到真实面试准备。**

采集、RAG、记忆和多 Agent 本身已有大量实现。可形成区分度的是具体人群、领域数据语义、可审查的证据和持续使用效果。是否有优势必须用对照验证，本次没有得出“优于竞品”的实验结论。

## 当前项目是否按方向发展

| 能力 | 核对到的实现 | 评估与边界 |
|---|---|---|
| 领域数据 | raw_items → postings/posts → 合并岗位、题目、chunks；官网及个人登录平台 | 是有价值的基础；覆盖、新鲜度和处理完成度需要分别衡量 |
| 同岗与冲突 | align/match.py 完全链接聚类，resolve 保留字段来源与冲突 | 已有领域工程深度；抽样错误率与下游影响需持续核查，不能只展示历史 F1 |
| 工具执行 | tools/runtime.py 统一参数校验、错误分类、局部请求约束、重复结果复用、预算及落库 | 与主线一致。日期守卫主要来自当前原话的有限规则，尚不是覆盖全部条件的统一任务契约 |
| 任务持久化 | agent/tasks.py 持久队列、请求 UUID 去重、同会话串行、不同会话最多四路、审批状态 | 与主线一致。后端重启把 running 变为 interrupted 或 waiting_approval；没有自动无缝续跑 |
| 上下文 | agent/main.py 清理前轮工具结果、摘要、长期记忆卡片 | 有实现；清除后提示重新查询，没有向模型开放按旧工具结果精确回读的完整路径。日志存在不等于模型可取回原证据 |
| 个人记忆 | 双时间线、候选抽取、冲突与确认、临时查询边界、删除审批 | 应维护已有能力。避免让临时查询变成长期偏好，复杂表述及跨模型还需验证 |
| 结果与证据 | results.py 只为成功工具输出中出现且回答引用的 ID 生成卡片 | 能限制虚构卡片；不证明回答每一句解释都受来源支持 |
| 匹配展示 | match.py 明确硬条件与未知；前端已有未提交语义修正 | 分数使用启发式权重，未知贡献 0.6，没有概率校准。资格状态、证据完整度与排序分应分别解释 |
| 评测 | 模块测试、真实任务快照、规则检查、辅助审查、轨迹落库 | 基础较充分；当前候选仍缺完整端到端验收，不需要先扩建通用评测平台 |
| 交付与运行 | 本地启动脚本、Docker、OWNER_TOKEN、手机配对基础 | 本次 3000/8000 未监听，数据库/图谱监听；未配置 Git remote、未核实公开演示。当前服务面向单个拥有者，不等于多租户产品 |

综合判断：**架构和实现方向一致，实际推进需要从“新增采集与逐例提示词修正”进一步收敛到“同一真实任务的完整验收与稳定交付”。** 继续使用现有 LangGraph、PostgreSQL、FastAPI 和前端即可。Neo4j 保持可选，在任务对照能证明收益时使用；不急于扩建图谱、多 Agent 或新平台。

## 本次新发现与验证

### 1. 岗位核验会把未知状态误判为关闭：优先级 P0

位置：`src/polaris/live.py:28,248,320`。

`_refetch` 对字节/小红书招聘页使用“命中 GONE_WORDS 或正文不足 80 字”判断页面消失；词表包含过宽的“该职位已”。随后对外返回 `online=False` 并说明页面已下线/删除/不存在。

本次使用本地合成页面替换抓取函数，没有联网或写业务库：

| 输入 | 实际分支 | 应有判断 |
|---|---|---|
| 11 字的加载提示 | 页面不存在 | 未能核验，需要重试或说明未知 |
| 149 字岗位正文，包含“该职位已更新” | 页面不存在 | 更新文案不证明关闭，应继续核验 |
| 132 字正常岗位正文 | 返回正文 | 对照路径正常 |

证据：已保存可随仓库携带的 [合成反例结果](2026-10-21-liveness-counterexamples.json)，原件仍在本机忽略目录 `data/probe/direction_liveness_probe_20261021.json`。这是逻辑反例，不是两个真实网站事故；未统计真实误判率。它可能让用户错误放弃岗位，优先级高于增加新工具。

建议返回“确认开放／确认关闭／无法核验”的状态，附原因和时间。网络/认证/页面未就绪归入无法核验；关闭必须有明确证据。HTTP 成功本身也不足以证明在招。

### 2. 采集尝试、成功与知识可用之间缺少完整的完成判据：P0

位置：`daemon.py:125` 的 official_done_today 不筛选运行成功状态；`run_round` 仅在 new_ids 非空时推进抽取与知识刷新；`extract.py:126` 按最旧 ID 取 pending。

影响：失败尝试可能阻止当天补跑；没有新增原文时，已有待处理内容不一定继续推进；“本轮抽取 N 条”可能主要是旧积压。此判断来自代码与前轮运行证据，不在本轮打断采集做故障注入。

建议逐阶段记录成功、失败、待处理及最后成功时间，按失败类型有界补偿。新的采集完成状态应依据可验证的阶段成果，不能只看执行过。验证“新抓取→可检索”延迟、最老积压年龄、失败后重新处理结果。

### 3. 本轮条件与长期画像可能导致卡片语义分歧：P1，待端到端核查

`results.entities` 默认用 `matches` 读取长期记忆画像；主 Agent 又允许用户本次查询改变范围而不写入长期记忆。这样“长期想北京，本次看上海”可能出现查询范围与卡片匹配解释使用不同条件的情况。

这是已确认的数据路径差异，尚未通过真实完整对话证明出现误导。应优先加入一个明确的临时改条件验收场景，展示“按本次条件”或“按长期偏好”的计算依据，再决定是否需要统一任务条件对象。

### 4. 上下文和恢复机制的能力边界：P1/P2

已有持久化、清理与摘要，不能把它们统称为所有故障自动恢复。首先把中断原因、已完成内容、可重试动作解释清楚。只有只读任务具备稳定结果记录与重放条件时，再做自动恢复；有副作用的步骤需要独立幂等依据。

旧证据回读可作为第二个纵向实验：比较重新查询、保留摘要、按保存结果 ID 取回三种策略的正确性、时效和成本。取回旧证据时必须带时间；“问当时依据”与“核验现在状态”应走不同策略。

### 5. 独立公开演示仍是交付阻塞：P0 交付项

`cli.py` 的 sandbox 是复制真实库后清理部分个人状态，不能视为纯合成公开库。`tools/jobs.py:201` 默认排除 synthetic，帖子/题目链路也有对应过滤，已有 synthetic fixture 不能自动保证完整演示可用。Docker compose 尚未包含前端服务；数据库构建依赖本地 vendor 目录。

建议单独建立演示数据域及可复现导入入口，覆盖岗位、面经、冲突、未知和故障样例；允许该独立实例查询合成内容，验证任何真实数据和登录状态均不进入演示。先在干净环境验证运行说明，再制作提交材料。

## 专业定位：明确自己要证明什么

建议以一个连续任务表达产品价值：

> 按我本次条件找岗位 → 判断信息是否新鲜及可信 → 解释符合、不符和未知 → 给出来源 → 根据所选岗位生成有依据的面试准备 → 记录我明确确认的跟进状态。

相比泛化求职助手，重点服务中国 Agent/LLM 实习：区分日常实习、校招、社招；处理学历、论文、到岗天数及时长；区分亲历面经与备考资料；保留时间与来源冲突。不从少量 offer 自述推断录用因果或给个人录用概率。

建议优先证明的两项技术能力：

1. **约束与证据贯穿的任务执行。** 用户条件进入工具、结果判断和卡片的口径一致；遇到空结果能诊断并有限补查；无法核验时保留未知。
2. **可审查、可中断并按边界恢复的执行过程。** 每步结果和状态可定位，重复请求不重复生效；是否自动恢复由动作性质决定。

上下文工程围绕这两项的失败再深入。评测为每次修改提供证据。该定位与 PURPOSE.md 现有主线一致，本报告不另建强制研发路线。

## 如何开发：顺序与验收产物

| 顺序 | 一轮要完成的工作 | 完成标准 |
|---|---|---|
| 第 1 轮：可信核验 | 修复关闭/无法核验混淆；把明确证据和原因返回工具层 | 加载、拦截、超时、真关闭、更新文案等案例分别判对；有结果的正常路径不退步；保存修复前后反例 |
| 第 2 轮：数据可用性 | 分清采集与后处理完成；补偿失败和积压；保持现有平台配额 | 没有新原文也能处理已有待办；失败不计作成功；新增可检索数量和延迟有记录 |
| 第 3 轮：端到端条件一致 | 完成现有卡片语义核查，验证临时条件、当前工具范围、长期画像及回答口径 | 不把未知当不符，不以高分抵消硬冲突；查询变化可解释；旧偏好不静默覆盖本轮条件 |
| 第 4 轮：对照与产品交付 | 在相同数据/模型下完成真实任务对照，打通纯合成演示与干净启动 | 有完整输入、工具过程、答案、保存状态和失败记录；他人按 README 能运行；界面与宣称一致 |
| 后续：按失败深入 | 若出现长上下文或中断损失，再做证据回读、只读恢复或并行研究 | 相比当前机制在预留新需求上有收益，报告正确性、耗时和成本；无收益则撤回 |

每轮先讲清问题与设计，再实现一个机制、展示结果，由作者理解和判断后进入下一轮。不同时启动三条独立平台研发线。比赛交付应优先保证一条核心任务与演示，不把完整的自动故障恢复系统设为所有交付的前置条件。

## 怎样形成可信的项目成绩

先冻结一批真实任务，建议 12–20 条覆盖正常、稀疏、无匹配、条件修改、来源冲突与工具故障；一部分在改动前预留。数字是建议的初始规模，不是统计充分性的保证。

- 基线 A：同一合法数据快照、同一用户条件，简单筛选/检索加模型回答。
- 基线 B：当前北极星候选；实验组只增加本轮一个机制。
- 每题多次运行，分别报告正确结果、约束错误、证据支持、合理工具行为、保存状态；环境问题单列。
- 比较完成时间、token 和可用数据延迟；费用只有完整计量且价格可核实时报告。小样本展示原始次数和失败案例，不包装成稳定 SLA。
- 已调试的题转为回归。关键事实由人工复核，模型审查为辅助。无岗位时正确拒绝也要证明没有因为检索遗漏误拒绝。
- 用户价值以自己持续使用、少量自愿试用者的反馈衡量：人工核对时间、有效岗位发现、误报漏报和准备材料的可用性。不能用 offer 数量直接归因模型效果。

竞品对照本轮只是功能与源码对照。若后续做性能比较，必须统一输入数据、模型和预算，并注明各项目支持场景；不能拿不同来源与默认模型的得分直接排名。

## 当前应控制的扩张

暂缓新平台数量、通用插件市场、复杂多 Agent 拓扑、强化学习训练、Kubernetes/微服务迁移及新的通用评分器。它们可以在对应瓶颈有证据后再讨论。现阶段更有说服力的成果是：完整展示一次真实任务，解释它过去为什么会错，哪个机制修正了它，以及新任务中还有什么没有解决。
