## 一条任务逐层做深

示例输入：找近七天北京的 Agent 研发实习，每周四天；输出适配理由、硬条件、未知信息、可回到原网页的证据，再给相关面试准备建议。“近七天”必须区分岗位发布日期、首次采到日期和最后核验日期。画像是示例，不声称是作者真实情况。

1. 先检查真实任务轨迹，把无结果区分为覆盖不足、检索遗漏、硬条件不匹配、工具故障、模型决策错误；环境故障单列。
2. 一轮只处理一类失败。优先验证合理补查与正确停止：不能放宽用户硬条件凑结果，登录失效不能回答没有岗位；补查也受时间和费用预算约束。
3. 该机制通过后，再验证保存状态和恢复：切页重连、后端进程退出分别测试；重复提交不产生重复业务写入；记录开始、等待、失败、取消及完成的真实状态。
4. 只有长轨迹出现遗忘、噪声或成本问题时，优化上下文：保留当前硬条件、必要证据和待办，原始材料可回读；最新条件覆盖旧偏好；外部文本不具有更改权限和系统规则的效力。
5. 自己持续使用，再邀请少量自愿同学试用，观察是否找到了原本遗漏的可投岗位、是否节省人工核对时间。公开实例使用合成数据。单用户规模如实说明。

采集链本身也要按“发现→抓取→抽取→合并→可检索→回答引用”逐阶段衡量。最近已观察到登录缓存与真实认证不一致、失败尝试被标成当日完成、旧抽取积压挤占新数据、进程终止后 running 记录未对账等风险。新抓到多少条不能替代新增可用知识的数量。

## 如何证明有效

- 固定数据快照、背景、时间、模型和版本，修改前预留新需求，重复运行；已用于调试的案例转为回归，不再叫未见测试。
- 检查结果、执行过程、保存状态三方面：条件遵守、来源支持、工具与参数选择、失败解释、实际落库。人工核对关键事实；模型裁判只辅助。
- 同时记录任务成功率及样本量、关键条件错误、证据正确性、重试与恢复结果、耗时中位数/P95、token、数据可用延迟与积压年龄。样本少时报告原始次数与范围，不编造稳定 SLA；费用仅在完整计量且有价格依据时报告。
- 历史 391 项自动测试通过证明相关回归检查通过，不代表用户任务成功率或生产验收通过。
- 每次保留一份失败轨迹、一项设计取舍、前后对照、剩余问题、回滚版本。只实现真实任务需要的可靠机制，不先扩成通用 Agent 平台。

## 阶段侧重点

比赛前：优先完成一条可演示且可复测的任务、必要可靠性修复、合成数据公开实例和提交材料。每个机制由证据决定是否保留。

比赛后：持续自用和少量试用，积累故障与反馈，再决定上下文、记忆、技能加载或可并行研究是否值得深入。多 Agent 需要相对单 Agent 的任务收益证据；SFT/RL 需要可靠任务轨迹、奖励或标注及相应对照，作为后续独立取舍。

最终希望能在面试中展示：一个具体需求为何失败，如何定位，为什么采用这个机制，在新需求上改善多少、代价多少、还有哪些边界。数字必须来自后续实测，不预写到简历。
