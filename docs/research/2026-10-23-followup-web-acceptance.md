# 网页跟进保存与重连验收（2026-10-23）

本轮用**现有网页组件、现有跟进业务接口、隔离 PostgreSQL 的合成岗位**，实际点击收藏、编辑状态和保存，刷新后读回。没有替用户记录真实投递，没有调用模型／招聘平台，也没有复制真实库。两条岗位均明确标为“合成验收”，同公司、不同岗位。

## 已验证的行为

1. 从对话结果卡打开岗位详情，初始未收藏、未投递；只查看没有新增进度。
2. 点击收藏后仍为未投递，产生独立的收藏事件。
3. 通过表单明确保存“面试中”、合成一面进度、备注；网页出现“已保存”。
4. 首次日期输入未真正触发控件更改，HTTP请求实际为 `next_followup: null`，接口读回也为空。保留这个失败，没有称日期已通过。用日期控件真实键盘事件输入、失焦确认保留后再保存，读回为2026-10-25。
5. 刷新重新请求数据库，卡片仍为已收藏／面试中；再次打开详情，进度、备注、日期2026-10-25均显示。对应三次明确保存（收藏、进度、补日期），历史3条／revision3。
6. 同公司另一岗位仍未收藏、未投递、无历史，不把公司的进度当成所有岗位的进度。接口读回与页面卡片一致。
7. 生产库 `job_followups` 与 `job_followup_events` 均保持0，本轮没有真实求职状态写入。

这验证的是明确网页操作的保存和刷新读取，不是模型理解任意“我投了某岗位”文本、真实投递、网络中断自动恢复或公开演示已完成。失败请求幂等及版本冲突已有隔离业务回归，本轮未额外模拟浏览器保存响应丢失。

## 新发现：最近采集截断了UTC日期

同一合成岗位，来源快照显示北京时间10-23，但卡片／详情最近采集显示10-22。`tools.jobs._job_row` 先对实际 `last_seen_at` 取UTC日期，前端拿到的已经是22，无法恢复为北京时间23。

修正 `5618432`：最近采集先换算为北京时间再取日期，列表和详情沿用同一结果；不修改数据库时间或来源本来就是日历日期的 `posted_at`。新6组检查覆盖北京时间午夜前一秒／午夜／凌晨、概要／详情，修前4失败2通过；修后与费用、岗位工具、结果／跟进、条件贯穿共**47通过**，4条既有ARRAY弃用告警。命令：
