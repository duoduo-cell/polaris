# 求职 Agent 完整应用场景调研（10-24 更新）

调研日期：2026-10-24 夜。在 [10-22 场景调研](2026-10-22-continuous-career-agent-scenario.md) 基础上更新：补最新本地数据、10-24 已做出的功能、新的对标产品，以及“爬竞争者个人信息”的边界。10-22 报告里的持续执行机制（第 6 节）、验证方法（第 11 节）仍然有效，这里不重复。

## 1. 一句话

**一个替你盯着求职目标的云端 Agent**：你交代一次经历，它按 HR 的眼光整理成证据档案，拿同类求职者的公开经历和你横向对比，查清岗位现状、最新进展和面经；然后在云端持续跟进你的目标岗位和同层次公司的岗位，有变化就报告，并不断更新“你现在还差什么”。

## 2. 典型场景：一个人从第一次对话到两周后

以下人物是合成的。

> “我 27 届本科，做过一个 RAG 项目和一段小公司后端实习，想找北京的 Agent 应用开发日常实习，每周 4 天、能干 4 个月。帮我看看我在 HR 眼里怎么样，和投同类岗位的人比差在哪，接下来两周帮我盯着。”

| 步骤 | Agent 做什么 | 用户看到什么 | 用到的能力 |
|---|---|---|---|
| ① 交代经历 | 抽取学历、时间、技能、项目、实习；只追问会改变判断的缺口（如“RAG 项目你负责哪部分、有没有评测数据”） | 一张求职卡：已知、待确认、可追问的点 | 记忆抽取、规则化更新 |
| ② HR 视角整理 | 按三个问题看：是否满足明确资格；经历能否支撑 JD 要求；技术面能否追问到真实工作 | “资格：全部满足；证据：检索有实现、缺评测数字；风险：项目只写了用了什么框架” | 结构化评估、证据绑定 |
| ③ 同组横向对比 | 找公开帖子里投同公司同方向的人自述的背景（学历层次、论文、实习、面到几轮、结果），按可比程度分组 | “近半年字节 Agent 实习拿 offer 的自述样本 5 人，3 人未写学校；有 2 人有大厂实习”，以及你和他们的差别、样本不够的提示 | 同类样本库、去重、主体识别 |
| ④ 查岗位现状 | 官网和招聘平台的在招岗位，发布时间、还在不在、要求原文；同岗位的面经题；“泡池子 / 开奖时间”等进展帖 | 3–5 个值得投的岗位 + 原文链接 + 符合/不符/待确认 + 面经原题 | 混合检索、匹配、来源核验 |
| ⑤ 开启持续跟进 | 生成一张跟进卡：盯哪些岗位、同层次范围（如“北京 Agent 应用开发日常实习，大厂 + 头部 AI 公司”）、检查频率、两周期限、通知方式、预算 | 一张可修改、可暂停的“委托” | 长期目标对象、调度 |
| ⑥ 云端高频检查 | 重点岗位按小时级轻量检查（只比字段是否变化），新岗位按来源节奏搜索；有变化才调模型分析；登录平台按本人账号、低频 | 无事不打扰 | 云端执行、变化检测、预算控制 |
| ⑦ 报告与态势分析 | 重要变化即时提醒（要求从 4 天变 5 天、岗位关闭、出现更匹配的新岗、新面经）；每天一份简报：新增/下架、同类人进展、你的差距变化 | “今天字节两个 Agent 岗下架、美团新开一个更匹配；最近 3 篇面经都问了工具失败恢复，你还没准备这块” | 事件影响判断、简报 |
| ⑧ 你的进展回流 | 你说“投了”“一面挂了，说项目深度不够”，或授权邮箱里出现面试邀请 → 更新进度、把拒绝理由写进短板、调整准备计划、起草跟进消息 | 漏斗、提醒、跟进草稿 | 跟进状态机、记忆、审批 |

“完全云端”的意思：上面 ⑤–⑧ 在你电脑关着时也继续，你用手机看进展、批准动作、暂停或改目标。

## 3. 这个需求是真的：本地数据里的证据

近 120 天本机采到的小红书 + 脉脉原文 **2,277 条**，按关键词粗略统计（关键词会误中，只作量级参考）：

| 话题 | 命中帖子 | 说明 |
|---|---:|---|
| 背景（bg、学历、本科、双非、985、论文…） | 885（约 39%） | 很多帖子开头就是“个人 bg：28 届 2 本 9 硕 0 实习” |
| Agent / 大模型 / RAG | 963 | 目标方向本身很热 |
| 面经（一面、二面…） | 513 | |
| 进度（泡池子、HC、排序、名额…） | 452 | 如“面完 HR 还在泡池子，听说 11 月开奖” |
| 同时有“背景 + 结果/进度 + Agent/大模型” | 136 | 可以拿来做横向对比的原始候选 |

典型帖子（转述，不含作者信息）：“28 届 2 本 9 硕、0 实习，分享第一段算法实习怎么找的”（近千赞、一千多收藏）；“27 届非 92 硕，一篇 ICML + 两段中小厂实习，两个大厂实习机会选哪个”；“字节/腾讯实习选择求助”。**大家本来就在用“晒背景 + 问结果 + 比进度”的方式求职，只是全靠手刷。**

但能直接拿来对比的样本很少。本机从帖子里抽出的同类求职者背景共 675 人，其中：

- 只有约 1/3 写了学校，331 人连公司都没识别出来；
- 具体到“字节 · 实习 · 拿到 offer · 近半年”只有 5 人，大多没写学校和论文；
- 都是发帖人自述，拿到 offer 的人更爱发，有幸存者偏差。

**结论：需求很强，但“同组竞争画像”的数据天然稀疏，产品必须如实说“样本只有 5 个”，不能装作有统计结论。**

## 4. 别人怎么做

| 产品 / 项目 | 做法 | 对北极星的意义 |
|---|---|---|
| OpenAI **Dots**（2026-09-29 发布） | 常驻 Agent，每个有自己的云端电脑和浏览器；没被派活时主动做研究，这时应用连接只读；需要批准或有急事才联系用户 | “云端持续负责”的产品形态标杆；主动研究期间只读、动作要批准，和北极星的边界一致 |
| Meta **Muse**（2026-09-08 发布） | 每个 Agent 一台云端虚拟机，关掉 App 也继续；批准请求在 App 里单独弹出、不在对话里（防止读到的内容冒充用户批准），有独立的权限 Agent；有活动记录、可随时撤销连接 | 审批与对话分离、活动记录，是“受控工具调用”的参考 |
| **LinkedIn Premium** 申请者洞察 | 平台用自己的申请者数据：你在申请者中的排名（只在前 50% 时显示百分比）、申请者的热门技能和你有没有、学历和经验层次；岗位至少 3 个申请者才显示 | **“和同组竞争者横比”在业界是平台方用申请者聚合数据做的**，不是爬个人主页 |
| **Boss直聘** 竞争力分析（付费） | 平台内对比你和其他应聘者；第三方评测认为岗位关联数据不准，结果可信度存疑 | 同上；而且说明这类对比数据质量本身就是难点 |
| **Jobright**（Orion） | 非关键词的语义匹配、找目标公司的内推人/校友、24 小时求职助手；独立评测说技术细分岗位回答偏泛 | 匹配 + 人脉 + 助手的组合已商业化；中国实习语义和证据是空白 |
| **智联 职悟空**（2026-07 WAIC） | 职业规划 → 简历 → 岗位匹配 → 模拟面试 → Offer 选择的全流程，免费 | 国内大平台已做“全流程助手”，但不是持续跟进、不做跨平台证据 |
| GitHub：career-ops、Job Hunter Team、ai-job-search、LinkedIn Job Alert Agent、JobSpy、changedetection.io、BossHunter、OfferGraph | 有的按需评估岗位并起草材料（从不替你投），有的 24 小时扫招聘网站打分，有的只是定时脚本 + 通知 | 单点能力都有人做了；**没有人把“同类样本对照 + 来源时效 + 长期目标负责 + 中国实习语义”连起来** |

所以北极星的区别不在“能匹配岗位”，而在：**对一个具体目标长期负责、每个结论有出处和时间、知道哪些不知道、能拿同类人的公开经历给出有边界的对比。**

## 5. “爬竞争者的个人信息”能做到哪一步

你举的例子是“把这个人毕业哪个大学、什么经历爬下来横向对比”。这要分三种情况：

| 做法 | 能不能做 | 理由 |
|---|---|---|
| 爬某个具体的人的个人主页（脉脉、LinkedIn 上的人） | **不做** | 《个人信息保护法》第 27 条允许在“合理的范围内”处理已公开的个人信息，但个人明确拒绝的除外，对个人权益有重大影响的要取得同意；第 25 条规定处理后不得再公开；平台用户协议禁止自动采集；项目早就定了“脉脉和 LinkedIn 上的人不做自动采集”。而且你根本不知道谁和你在同一个 HC 里竞争 |
| 用公开面经帖里**作者自述**的背景做匿名聚合对比 | **做**（已有 675 人的样本库） | 作者主动公开、用于求职经验交流，北极星只做聚合统计和带出处的匿名案例，不输出“某某人” |
| 平台给你本人的竞争力数据（Boss 竞争力分析、LinkedIn 申请者洞察） | **可以作为一种来源**，需要你本人账号、只读、低频 | 这是平台用合规数据算的聚合结果，最接近“真正的同组竞争”；但可信度要标注 |

这条边界本身就是面试时能讲的亮点：**知道什么数据能用、怎么在数据稀疏和合规约束下仍给出有用的判断。**

## 6. 北极星现在做到哪了（10-24）

| 场景步骤 | 已有 | 缺的 |
|---|---|---|
| ① 经历抽取 | 记忆卡 21 个属性，规则化更新、改口要确认；被拒反馈写回卡片（10-24） | 经历 → 本人职责 → 产物 → 结果的证据链；读简历和 GitHub |
| ② HR 视角 | 逐岗硬条件、技能待确认、学历/论文门槛解释 | 一份“HR 三问”整体评估报告 |
| ③ 横向对比 | 675 人的同类样本库、peers_search 工具、未知和样本少的提示规则 | 按同职能/同招聘季/同公司分组；“你—JD—样本—缺口—行动”对照表；本轮没在网页上验证过 |
| ④ 岗位与面经 | 629 个岗位（539 在招、90 已下架）、3,853 道面经题；官网每日快照判断下架；先筛后排的检索、证据门禁（10-24） | 同一岗位要求变化的字段对比提醒；“泡池子/开奖”进展时间线 |
| ⑤ 跟进卡 | 无（现在是全局画像 + 常驻采集） | 按具体目标维护：关注对象、同层次范围、频率、期限、预算、暂停 |
| ⑥ 持续检查 | 本机常驻采集（官网每日、小红书/脉脉/Boss 低频）、后台启动脚本（10-24） | 按目标调度、轻量变化检测、云端运行 |
| ⑦ 报告 | 主动推送规则 + 每日简报 + Windows 通知 | 变化 → 影响 → 建议的态势分析；手机能收到的渠道 |
| ⑧ 进展回流 | 投递状态、跟进草稿、被拒回写、投递漏斗（10-24） | 授权邮箱自动识别面试邀请/拒信；日历 |
| 云端 | 无，全部在本机 | 云上的调度、数据库、Agent、通知；登录平台如何处理 |

**10-25 更新**：⑤ 跟进卡、⑥ 按卡检查变化（读本地库）、⑦ 分级提醒和态势报告、② HR 视角、③ 三层同类对照已经做出来并在网页上实测（见 [设计](../design/WATCH.md) 和 STATUS）。仍缺：经历证据链（读简历）、邮箱/日历、云端运行。

## 7. 能体现什么（面试官和 HR 看什么）

对照大厂 Agent 实习 JD 里常见的要求：

| JD 要求 | 这个场景里能拿出的证据 |
|---|---|
| Agent 编排、长任务 | 一个跨天的跟进目标：重启、暂停、改条件、重复事件后仍然正确继续 |
| 工具调用、连接外部系统 | 官网/社交平台/邮箱/日历/GitHub 的工具契约、权限、审批、预算；MCP 出口 |
| 上下文工程、RAG | 已有真实案例：后过滤丢召回（1→32）、工具结果预算、提示词约束不住时在编排层加证据门禁 |
| 数据工程 | 采集 → 抽取 → 多来源对齐 → 时效与“没看见”区分 |
| 评测 | 事件回放：JD 变化、关闭、超时、重复通知、改条件；漏报/误报/打扰次数 |
| 安全与合规 | 个人信息边界、外部帖子里的注入、对外动作只起草 |
| 产品意识 | 作者自己就是用户；用“找到的可用机会、省下的核查时间”而不是“帮多少人拿 offer”来衡量 |

最有说服力的不是功能清单，而是几段“真实跑起来 → 发现问题 → 怎么改 → 怎么证明改好了”的故事。10-24 已经攒了四个，见 DEVLOG。

## 8. 难点在哪

1. **对比数据稀疏且有偏。** 具体到一个公司一类岗位只有个位数样本，学校只有 1/3 写了，拿到 offer 的人更爱发。难在“说出有用的话，同时不装作有统计结论”。
2. **时效和“没看见”。** 页面加载失败不等于岗位下架；同一个链接内容变了，可能只是页脚变了；搜索结果变少可能是采集坏了，不是市场变冷。
3. **长期执行的可靠性。** 定时、外部事件、用户改条件交错发生；重启、重复执行、旧条件失效、通知发出后进程挂掉，都不能漏报也不能重复报。
4. **登录平台上云。** 小红书、Boss、脉脉要本人账号，有风控；本机已经遇到 Boss 令牌被拒、小红书“访问频繁”限流，云端 IP 只会更难。可能只能“公开来源上云、登录平台留本机”。
5. **主动但不打扰。** 高频检查不等于有用；什么值得即时提醒、什么进简报、什么不说，要靠用户反馈调。
6. **成本。** 检查次数 × 来源数 × 模型调用；必须做到“没变化不调模型”。
7. **怎么证明有用。** 录用结果受太多因素影响，只能测：找到的可用机会、提醒命中率、漏报、用户核查时间。

## 9. 重要的开发方向（按顺序）

| 顺序 | 方向 | 做完的标志 |
|---|---|---|
| 1 | **跟进卡（长期目标对象）**：把“全局采集”变成“为你这个目标负责”——关注岗位、同层次范围、频率、期限、预算、暂停 | 网页上开一张跟进卡；采集和分析按卡调度；改条件后旧条件不再触发 |
| 2 | **变化检测 + 态势报告**：岗位字段级对比（天数、要求、关闭）、新同类岗位、新面经、同类人进展 → 判断对你的影响 → 即时提醒或进简报，并显示“哪些来源今天没查成” | 回放一周事件：重要变化不漏、无变化不重复、来源故障不冒充“没变化” |
| 3 | **HR 视角档案 + 同类样本对照**：经历证据链（读简历/GitHub 只读）；“你—JD—样本—缺口—行动”五列表，样本不足时如实说 | 合成用户的对照报告每条结论有出处，样本数和未知都写清 |
| 4 | **云端子集**：先把公开官网采集、主 Agent、数据库、调度、一个手机通知渠道搬上云；登录平台留本机并标注“依赖本机” | 作者电脑关机 24 小时，云端照常检查和提醒；手机能暂停 |
| 5 | **连接器**：授权邮箱识别面试邀请和拒信，日历查冲突 | 广告邮件不误报、同公司多岗位不串线 |
| 6 | **事件回放评测**：12–20 条事件序列做回归 | 每次改动报告漏报、误报、打扰、成本 |

第 4 步要先和用户定：用哪家云、每月预算、通知渠道、哪些来源上云。这些都还没定，10-24 用户也明确了换模型、部署暂时不做。
