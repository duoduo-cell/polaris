# 研发日志

只有这一个文件，持续更新：最新的一轮写在"轮次"的最上面。只记以后用得上的：决定、发现、改了什么、结果、学到什么。
详细数字看 `eval/reports/` 和 `design/DEPTH.md`；目标和工作方式看 `PURPOSE.md` 的"现在的目标"。

## 现在在做什么

侧重点：工具调用与任务编排（agent 的驾驭层）。每一轮：摊开真实记录 → 作者判断 → 归类计数 → 作者挑一类 → 只改一处 → 量前后（含没见过的题）→ 作者决定留下或撤回。

## 轮次

### 第 1 轮（进行中，10-12 开始）

- **第 1 步（等作者）**：用自己真实想问的问题问北极星 20 次，每条点"对"或"有问题"并写一句"应该怎样、实际怎样"（存本机 `data/feedback/answers.jsonl`）。
- 看的时候多留意这六件事（都是做过生产的人真实遇到的）：为找不存在的东西一直查；来源靠不靠谱；查够了停没停；工具出错有没有告诉你；快不快、长不长；有没有做不该做的事。
- 之后：把每句判断和对应的查询过程对上，归类计数，作者挑第一个要改的。

## 课堂笔记

### 一次回答里发生了什么（10-12）

问"按我的条件推荐 3 个北京的 Agent 实习"（评测库、合成用户、提示词 v14）：169 秒，模型想 5 轮，调 13 次工具，推荐字节 3 个岗位，回答约 3,300 字。

| 轮 | 模型用时 | 做了什么 |
|---|---|---|
| 1 | 12 秒 | 同时发两种搜索：按关键词相关度；只按条件筛（北京、实习、Agent、每周不超过 4 天，另报 68 个 JD 没写天数） |
| 2 | 23 秒 | 翻页、单独搜腾讯和小红书（都是 0）、看 2 个详情 |
| 3 | 18 秒 | 看 4 个详情、图谱数北京 Agent 岗按公司分 |
| 4 | 52 秒 | 只搜一次面试题 |
| 5 | 54 秒 | 写回答 |

- **编排**就是模型每一轮的选择：查什么、一次并行查几个、什么时候停下来写。工具是我们写的程序，模型只决定调哪个、带什么参数。
- **时间几乎都在模型身上**：13 次工具不到 10 秒，模型 159 秒。要变快，该减的是轮数和废话。
- **每轮都要重读前面所有内容**：输入从 6 千涨到 2.4 万 token（一个汉字约 1 个多 token），这就是上下文。

### 做过的人遇到了什么（10-12）

- **吴恩达**：团队改进 agent 的速度，最大的预测因素是有没有纪律地做评测和错误分析；agent 输出花样多，错法也多。（[文章](https://www.deeplearning.ai/the-batch/improve-agentic-performance-with-evals-and-error-analysis-part-1)）
- **Anthropic 多 Agent 调研系统**（[复盘](https://www.anthropic.com/engineering/multi-agent-research-system)）：
  - 真实出过的毛病：简单问题开 50 个子 agent；为找不存在的资料一直搜（就是我们的 E2、H1）；查询太长太具体反而搜不到；偏爱内容农场。
  - 做法：用约 20 个真实问题开始就能看出大问题；按问题难度规定查几次；工具说明改好后用时少 40%；工具出错要告诉 agent；全程追踪；出错从检查点续跑。
- **Manus**（[上下文工程](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）：
  - 缓存命中率是生产里最重要的指标（缓存过的输入便宜约 10 倍）。我们的系统提示词里记忆卡片放得靠前，记忆一变后面的缓存就失效，这是一个候选改法。
  - 出过错的记录留在上下文里；长任务反复重写待办清单防跑偏；不中途删工具；太长的结果放外面、只留能找回的线索。
- **生产故障清单**：工具悄悄失败（返回坏数据，模型照编）；循环和费用失控；上下文被噪音塞满越跑越笨；失败会累积，每步 5% 失败率，多走几步就是两位数。我们 10-12 阿里云欠费那次就是工具失败。
- **控制**：2025 年 7 月 Replit 的 agent 在用户说"冻结"时删了线上库，复盘结论是缺闸门（开发和线上没分开、高风险操作不用批准、权限过大）。（[复盘](https://codenotary.com/blog/when-ai-goes-rogue-the-replit-incident-and-its-lessons)）面试问"怎么控制 agent"就答五样，每样指到代码：

| | 北极星现在 |
|---|---|
| 权限 | 采集只读；投递、发消息只起草；现查不对外开放 |
| 审批 | 删记忆要批准；记忆改口没说清先问 |
| 预算 | 模型最多 12 轮、每种工具有上限、现查最多 3 次、查满 10 次提醒收尾 |
| 追踪 | 追踪页、每次回答的时间线、所有调用入库 |
| 隔离和恢复 | 沙盒库、评测库与真实库分开；能中途停止；任务中断能接着跑 |

## 之前的开发（10-10 到 10-12，压缩版）

模块 M0–M7 已完成，入口和指标见 `STATUS.md`。下面只留以后面试或排错还用得上的：

- **最难的 bug**：新库第一句话卡死。LangGraph 检查点建索引用 CREATE INDEX CONCURRENTLY，恰好发生在登记会话的事务里，自己等自己。改成启动时在事务外先建好（`main.ready`），加了能复现的回归测试。
- **真实问答探针四轮**（`design/DEPTH.md`）：修了把查本地库说成现搜、说"没法记"、公司级进度丢失、每轮都压缩上下文（14 → 0 次）、撞调用上限把报错当回答；最慢一轮 365 → 148 秒。
- **回答质量评测七个版本**（`design/DEPTH.md` 第四轮）：能稳定量出来的改进都来自确定性改动（给工具补参数、刹车、编号识别、检索兜底），单题最多工具调用 27 → 12–14 次；提示词后几版在波动之内；v11 让诚实分下降、开始编编号，撤回。留出集抓到过一次过拟合。
- **评测器自己的错**：第一轮 3 个失败里 2 个是评测器的错；打分模型看不到工具返回、截断、缺前几轮依据、把打算和否定当成声称。生成和打分分开，换打分方式后所有轮次只重新打分。
- **线上问题**：统计和趋势里的编号点不开；岗位不能按每周天数筛；帖子题目被输出上限裁掉、模型顺着编号推；图谱只有一份、和复制库对不上，还把下架岗位算进去；向量服务出错整个搜索报错（现退回关键词和图谱）。
- **安全和控制**：网页以前对所有网卡开放，公共 Wi-Fi 下别人能打开，现在默认只听本机；手机模式要扫码配对；追踪和原始数据接口加口令；删记忆要批准。
- **网页**：切模块丢进度（会话状态移到根布局 + 后台任务入库）；对标 Dots、Manus、Claude 改版；追踪页；手机版（抽屉导航、可添加到主屏幕、Tailscale 远程）。
- **数据**：面经题按公司归属保守修复（1,024 道 → 902 道面经题 + 122 道备考题）；官网每天整批重采、标下架；现查工具与常驻采集共用额度和锁。
