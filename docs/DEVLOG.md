**重新核查调用失败**：24次留出/测试任务的21次拒绝或失败中，16次是未经允许移除/扩大日期窗口或把发布时间换成更新时间，3次是重复检索触及次数上限。另2次均为kg_stats提示“知识图谱没有启用”：为隔离未冻结的共享图谱，评测进程主动关闭了它，这2次属于评测环境/工具可用性处理，不能直接说成线上产品故障。124次执行成功中仍可能有参数或归纳错误，这21次不是所有错误的完整分母，也不是线上生产事故率。

**研发重心纠正**：前一阶段审查器改动较多；接下来的产品迭代优先处理“空结果后的有限补查和正确收尾”，减少重复/无必要调用，保持用户范围、明确数据不足及排除原因。修正记录要变成回归案例，并用新的未见需求验证，不把已经跑过的测试重新叫留出。不采用增加一堆Agent/工具或继续堆评分器来代替这项修复。

### 真实任务评测重建（10-12至10-13夜，进行中）

**目标**：作者明确要求真正衡量“工具成功调用、编排合理、结果有用”，不以完成对话算成功。旧平均打分可以掩盖事实错误，不能拿旧v14的24/24支持当前版本。

**预先固定题集**：`eval/gold/tasks_v3.json` 共12题，开发/留出/测试各4题，标明原始需求或场景改写来源。包含近3天岗位、缺少符合条件的岗位、offer背景、实习/校招/备考区分、带原句的题目、第二个岗位指代、多公司比较和无需工具的请求。留出和测试现已各生成12次，旧开发题仍不算留出。借鉴 [BFCL多轮执行验证](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html) 与 [τ-bench重复可靠性](https://arxiv.org/abs/2406.12045)，不是这两个官方benchmark的分数。

**冻结与公平比较**：新建专用副本 `polaris_eval_tasks_20261012`，未覆盖已有live/test或真实库；原始备份在忽略目录。固定时钟为快照时刻，记录业务数据、题集、系统提示与原始背景哈希；每题每次恢复同一背景、独立会话。原始网页现查关闭，共享图谱未冻结所以在评测进程禁用。原文只存 `data/eval/real_tasks/`。新跑法 `scripts/dev/real_task_eval.py` 支持先生成后评分，裁判失败不会丢失回答；旧失败记录不覆盖。副本修改加会话锁且不持有长事务，不能并发重置正在答题的背景。

**基线证据**：v17开发4题各3次，12次已生成：实际工具调用84次，82次成功，2次触发本地查询次数上限；用时p50为75.195秒、p95为116.56秒。这些只是执行指标，不是任务通过率。第一次评分网络连接失败，主动取消的是核对过身份的评测进程；从数据库恢复了已完成回答/工具证据，API和采集未操作。修复了评测自身两处错误：基线恢复时先恢复facts再恢复events；“最多三个”不是必须把不适合用户的唯一命中硬推荐。

**新发现的真实缺陷**：D1只命中伦敦、博士/顶会门槛的研究实习，不能当作者首份实习的可投推荐；某次重复搜索到达本地上限。D2三次均受背景丢失影响：`data/profile.md`明确说没有实习、没有论文，记忆属性表不支持这两项，回答反而重新问作者有没有。新增两个背景属性并沿用已有更新/冲突规则，不扩展新记忆算法或改视觉。真实抽取对照：明确零经历保留两项，未提背景的控制句不生成零经历；候选基线已保留无实习/无论文，原始缺失基线仍保留供对照。候选开发集正在重复生成，尚无收益结论。

**裁判本身也要验收**：最初flash裁判混同帖子作者和使用者、伪造引句；不接受其评分。plus裁判在三个已知控制例中识别五节点冒充五轮、第一段实习冒充已有经验及因果，正确识别备考整理。连续原文引句用代码核对，只忽略空白/Markdown强调，不更改数字或词句；引句不在原文时保持待审，不能降低门槛凑通过。完整任务裁判仍有不连续引句、把工具汇总当原文等问题，所以任务通过率尚未成立。按 [百炼官方文档](https://www.alibabacloud.com/help/en/model-studio/deep-thinking) 在评测裁判进程关闭qwen3.5思考；没有改服务配置或.env。

**结论**：只靠现有文字答不了"拿到 offer 的人几篇论文"这类问题，要靠读图和新的搜索词采来的数据，等常驻采集用新代码跑几轮后再验收一次。

**验收二：真实问答（评测库，作者真实背景，提示词 v15，10-12 20:30）**

问"最近一个月拿到大厂 Agent/大模型实习 offer 的人什么背景、我差在哪"和"字节算法/后训练实习最近有人面过吗"。
两题都先调 `peers_search`，回答都写了日期、距今天数、样本量、R- 编号，并逐项对照作者背景。只看形式就算过了；**逐条对原文核对**才发现问题：

| | 结果 |
|---|---|
| 核对的事实 | 22 处，21 处原文里有 |
| 错的那类 | 工具把"没写实习"返回成空列表，模型说成"R-997、R-533 是 0 实习拿到的"。两条原文都没提实习；R-997 补读图片后抽出了 Momenta 实习 |
| 改法 | 工具区分"没写（不等于没有）"和"原句写了没有实习"（只看本人原句）。在 308 个没写实习的人上试：7 个命中，全是本人自述，正文里"有没有实习岗""没有实习薪资"这类不再误判 |
| 改后重跑 | 144 → 58 秒；回答主动说"没写不等于没有"；新出现的 10 处事实全对 |
| 没处理 | 第二题回答里冒出一个无关词"Hermes："，模型输出噪声 |

**验收三：读图（手动补读 10 条老笔记）**

- 10 条都有图、都读出了字：共 34 张图、17,780 字。一半是只有标题的封面（每条 23–41 字）。
- **人和背景几乎没变**：17 人 → 17 人，写了实习的 5 → 6（R-997 补出 Momenta）。图里主要是面经题、时间线、offer 截图。
- **面经题被三处丢掉**：
  - 抽取只读前 6,000 字，而图片文字排在评论后面；
  - 每帖最多 15 题；
  - 同步题目时"正文"只取标题和描述，图里的题找不到出处，挂不上轮次。
  改成正文 → 图片文字 → 评论依次放、读 12,000 字，题目上限 40，图片文字算正文（抽取提示词 v4）。
- **评论没翻下去**：帖子显示 60–78 条评论，库里每条只存了第一页 10 条。拿一条实地查：鼠标不在评论区上时滚轮不起作用；放到评论区上后，要滚两三次到底才加载下一页 10 条。改成先把鼠标放到评论区，连续 3 次没变多才停。
- 识别结果里有 HTML 标签和代码块标记（占 7%），加了确定性清理。

**学到的**：
- 只验"有没有写日期和样本量"是不够的，要抽事实回原文对。
- 工具返回里"空"和"零"必须分开写，模型会把空列表读成 0。
- 采集层的毛病（滚轮、截断、上限）都是安静地少拿数据、不报错，只有拿"帖子上显示几条"对"库里存了几条"才看得出来。

**结论**：瓶颈在数据层和"往下挖"的工具，不在编排策略。侧重点仍是工具调用与编排，但要按真实的深度调研来做：
打开帖子 → 读图 → 翻完评论 → 看作者其他帖子 → 和 JD、日期对上；同时把"人和结果"抽成可查的记录。
原来的 20 道题作废，等数据能支撑后，和作者一起按"时效 + 同阶段背景 + 结果和难度 + 变化"重写。

## 课堂笔记

### 一次回答里发生了什么（10-12）

问"按我的条件推荐 3 个北京的 Agent 实习"（评测库、合成用户、提示词 v14）：169 秒，模型想 5 轮，调 13 次工具，推荐字节 3 个岗位，回答约 3,300 字。

| 轮 | 模型用时 | 做了什么 |
|---|---|---|
| 1 | 12 秒 | 同时发两种搜索：按关键词相关度；只按条件筛（北京、实习、Agent、每周不超过 4 天，另报 68 个 JD 没写天数） |
| 2 | 23 秒 | 翻页、单独搜腾讯和小红书（都是 0）、看 2 个详情 |
| 3 | 18 秒 | 看 4 个详情、图谱数北京 Agent 岗按公司分 |
| 4 | 52 秒 | 只搜一次面试题 |
| 5 | 54 秒 | 写回答 |

- **编排**就是模型每一轮的选择：查什么、一次并行查几个、什么时候停下来写。工具是我们写的程序，模型只决定调哪个、带什么参数。
- **时间几乎都在模型身上**：13 次工具不到 10 秒，模型 159 秒。要变快，该减的是轮数和废话。
- **每轮都要重读前面所有内容**：输入从 6 千涨到 2.4 万 token（一个汉字约 1 个多 token），这就是上下文。

### 做过的人遇到了什么（10-12）

- **吴恩达**：团队改进 agent 的速度，最大的预测因素是有没有纪律地做评测和错误分析；agent 输出花样多，错法也多。（[文章](https://www.deeplearning.ai/the-batch/improve-agentic-performance-with-evals-and-error-analysis-part-1)）
- **Anthropic 多 Agent 调研系统**（[复盘](https://www.anthropic.com/engineering/multi-agent-research-system)）：
  - 真实出过的毛病：简单问题开 50 个子 agent；为找不存在的资料一直搜（就是我们的 E2、H1）；查询太长太具体反而搜不到；偏爱内容农场。
  - 做法：用约 20 个真实问题开始就能看出大问题；按问题难度规定查几次；工具说明改好后用时少 40%；工具出错要告诉 agent；全程追踪；出错从检查点续跑。
- **Manus**（[上下文工程](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）：
  - 缓存命中率是生产里最重要的指标（缓存过的输入便宜约 10 倍）。我们的系统提示词里记忆卡片放得靠前，记忆一变后面的缓存就失效，这是一个候选改法。
  - 出过错的记录留在上下文里；长任务反复重写待办清单防跑偏；不中途删工具；太长的结果放外面、只留能找回的线索。
- **生产故障清单**：工具悄悄失败（返回坏数据，模型照编）；循环和费用失控；上下文被噪音塞满越跑越笨；失败会累积，每步 5% 失败率，多走几步就是两位数。我们 10-12 阿里云欠费那次就是工具失败。
- **控制**：2025 年 7 月 Replit 的 agent 在用户说"冻结"时删了线上库，复盘结论是缺闸门（开发和线上没分开、高风险操作不用批准、权限过大）。（[复盘](https://codenotary.com/blog/when-ai-goes-rogue-the-replit-incident-and-its-lessons)）面试问"怎么控制 agent"就答五样，每样指到代码：

| | 北极星现在 |
|---|---|
| 权限 | 采集只读；投递、发消息只起草；现查不对外开放 |
| 审批 | 删记忆要批准；记忆改口没说清先问 |
| 预算 | 模型最多 12 轮、每种工具有上限、现查最多 3 次、查满 10 次提醒收尾 |
| 追踪 | 追踪页、每次回答的时间线、所有调用入库 |
| 隔离和恢复 | 沙盒库、评测库与真实库分开；能中途停止；任务中断能接着跑 |
